## 阶段 1：真实多进程并发验证

### 环境与入口

- 在现有测试入口上扩展，沿用隔离设施原则；具体工具在实施前核对现有 runner 的扩展位置。
- 启动两个独立 JVM，监听不同的本机端口，共享同一套专用 MySQL 和 Redis；记录 PID、端口、源码版本与测试配置。
- HTTP 客户端直接请求两个端口，不跟随 302。通过同一对端 IP 验证共享限流身份。
- 测试使用唯一运行标识、独立 Compose 项目/数据库及所需 RabbitMQ vhost。清理仅针对本次创建的进程与设施。
- 启动采用就绪检查和有界超时；失败时保存诊断结果并释放资源。配置与日志不保存秘密值。

### 必须覆盖的场景

| 场景 | 操作 | 核心断言 |
| --- | --- | --- |
| 创建额度跨实例共享 | 在两个端口交替发起创建请求 | 总放行数遵守同一令牌桶配置；切换实例不会得到新额度；被拒绝请求不发号、不插入映射 |
| 最后一个令牌并发争抢 | 预先消耗额度，再同时向两个进程发起请求 | 受控补充时间窗口内只放行剩余额度；无并发超发；429 的 Retry-After/no-store 正确 |
| 跳转额度共享 | 跨端口、跨短码混合 GET/HEAD | 两进程共享额度；HEAD 无响应体；拒绝请求无统计 Cookie、无访问事件 |
| 管理请求共享与隔离 | 跨端口调用管理写及统计查询 | 管理写与查询使用各自共享桶；无效鉴权不占额度；公共跳转与管理额度独立 |
| 禁用及重新启用跨实例可见 | A 完成状态变更，随后通过 B 访问 | 已确认协调后的新请求看到正确状态；403/302及自然过期的410符合契约 |
| 迟到的旧缓存回填 | 控制 B 的旧读取与 A 的状态变更交叠 | 旧版本结果不能覆盖新版本；变更完成后的新请求不接受迟到旧状态 |
| 每实例请求合并 | 两进程分别产生同码交叠 miss | 验证实例内查询减少；允许两个进程各发起一次查询，不要求集群全局只查一次 |

并发场景使用屏障、受控数据库阻塞或明确同步信号建立交叠；不依赖偶然调度与固定长时间 sleep。所有阻塞均设置超时及 finally 清理。需要查询计数时优先使用可解释的实际数据库证据，禁止公开测试控制接口。

### 验收

- 两个 PID 和独立端口可核对，请求确实覆盖两进程。
- 每个场景有输入、状态码、核心断言及结果记录；缺少设施或进程启动失败时明确失败，不静默跳过。
- 关键并发场景重复执行，仍满足断言；失败报告保留可定位的安全诊断信息。
- 运行结束无遗留进程或本次测试设施，现有用户服务与数据不受影响。

## 阶段 2：可复现持续负载测试

### 工作负载

| 工作负载 | 数据与缓存准备 | 主要观察 |
| --- | --- | --- |
| 缓存命中 | 预热已存在、启用且有效的映射 | 成功吞吐与延迟、实际映射查询数、CPU与连接池使用 |
| 不同短码缓存未命中 | 准备足量已存在映射，避免重复使用已预热短码 | 回源吞吐、SQL次数、实际加载并发、503及数据库等待 |
| 同码集中缓存未命中 | 每轮针对专用短码清除缓存，发起受控交叠请求 | 每实例合并效果、查询次数、等待与超时；单独报告突发结果 |

持续负载报告以命中和不同码 miss 为主；同码集中 miss 用重复受控突发验证。不存在码的404、HEAD请求及成功GET分别统计，不混入成功跳转吞吐或PV。

### 两种配置口径

1. 默认配置：保留默认限流和回源预算，观察正常额度与拒绝行为，分别统计302、429、503及其他结果。
2. 独立测试配置：在隔离环境明确提高限流额度，使其不成为主要瓶颈；保留并记录其他保护设置，观察给定条件下的处理能力。报告注明全部覆盖值，不修改日常运行配置。

多进程负载直接分配至两个端口，并记录分配比例；先保留单进程基线，在相同数据、配置和负载条件下比较。回源许可是每实例上限，两个进程的总预算可能叠加，必须写入解释。

### 采样方法

- 在实施时根据本机资源确定三个递增负载档位，先做短预检，再执行正式采样；不预设项目能达到的QPS。
- 每档预热至少30秒、正式采样至少2分钟，正式测量至少重复三轮。固定并记录数据规模、连接复用、客户端超时和请求类型。
- 到达率驱动工具设置有限并发和有限待处理预算，记录实际发起速率、调度延迟与未发出请求；不得无限排队或把客户端排队隐去。
- 汇总成功吞吐、各状态码数量/比例、网络错误、成功响应p50/p95/max、CPU/内存、连接池、加载在途和SQL计数。成功与拒绝延迟分别报告。
- p99仅在成功样本足够且重复结果可解释时报告，首轮以每场景累计至少一万成功样本作为展示门槛；不足时注明样本量并省略p99。
- 负载发生器与服务同机时，报告资源竞争及发生器是否达到设定速率；无法排除发生器瓶颈时，不作最大容量结论。

### 验收与交付物

- 单一命令能够准备数据、运行指定工作负载并产生报告；参数含实例数、负载档位、持续时间与重复次数。
- 每次运行建立独立目录，保存运行清单、原始请求结果或直方图、资源采样和汇总Markdown/JSON。
- 清单记录提交SHA、工作区是否干净、相关源码/配置指纹、JDK及依赖版本、操作系统、硬件和设施资源限制；脱敏配置足以复现测试条件。
- 报告给出三轮差异，解释限流、回源保护和数据库查询对结果的影响；不以一次最好成绩作为结论。
- 文档链接测试入口和原始结果。正式证据的归档位置及保留策略明确，避免仅引用可被清理的target目录。
- 若观察到饱和，说明本机及配置边界；若未观察到，只报告已测范围。

## 后续扩展

### 阶段 3：持续负载下故障与恢复

先形成稳定基线，再分别停止/恢复Redis与RabbitMQ。记录故障前、中、后各时间段的成功与拒绝分布、核心就绪、实际数据库加载、连接池与消息积压。核对创建/管理的业务前503、跳转降级和回源准入、MQ故障下核心跳转及恢复行为。故障注入仅作用于本次测试设施。

### 阶段 4：异步统计积压与排空

使用真实GET产生事件，降低或暂停消费形成积压，再恢复消费。分别记录HTTP跳转、事件交接、发布确认、消费结果和已记录事件。对受控确认事件检查eventId去重，对允许漏记的边界单独解释；统计查询可见延迟、积压峰值、恢复后排空时间和资源变化。不得由发布ACK推断已经写入数据库。
