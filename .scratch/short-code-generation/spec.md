# 阶段 2：短码生成机制

## Problem Statement

现有短链接 MVP 可以创建映射并完成跳转，但短码由固定 8 位小写字母和数字随机生成。项目希望在多应用实例共享一个 MySQL 主写库的部署前提下，改用可解释、可验证的发号和编码机制，让短码外观不直接呈现自增顺序，同时将长度控制在 4 至 8 位。短码是公开标识，不承担授权或保密职责；项目不以超大规模写入吞吐为当前目标。

## Solution

创建者沿用现有流程，即可获得 4 至 8 位、由大小写字母和数字组成的短码及完整短链接。复制、打开和跳转行为保持不变；多个应用实例同时创建时仍能得到不同的短码。创建失败不会向调用者交付部分完成的短链接。

## User Stories

1. 作为匿名创建者，我希望沿用现有创建接口提交原始 URL，以便无需学习新的创建流程。
2. 作为匿名创建者，我希望成功响应继续包含短码、完整短链接和到期时刻，以便立即复制或打开短链接。
3. 作为匿名创建者，我希望短码只包含大小写英文字母和数字，以便在 URL 路径中直接使用。
4. 作为匿名创建者，我希望短码长度始终为 4 至 8 位，以便短链接保持简短且不超出约定上限。
5. 作为匿名创建者，我希望系统明确只保证 4 至 8 位的长度范围，以便不会误以为各长度会均匀出现。
6. 作为匿名创建者，我希望短码外观不直接显示创建顺序，以便公开地址不呈现明显的自增数字。
7. 作为匿名创建者，我希望即使多个应用实例同时处理创建请求，也不会得到与其他映射重复的短码，以便新链接可以可靠使用。
8. 作为匿名创建者，我希望同一原始 URL 的不同创建请求仍产生独立映射，以便各链接继续拥有自己的期限和启用状态。
9. 作为匿名创建者，我希望系统发号成功而映射写入失败时返回创建失败，以便不会误以为已获得可用短链接。
10. 作为匿名创建者，我希望一次短码主键冲突后系统自动重新发号并再试一次，以便偶发异常不立即使请求失败。
11. 作为匿名创建者，我希望第二次仍冲突时收到稳定的创建失败响应，以便知道本次没有得到新映射。
12. 作为匿名创建者，我希望其他数据库错误不被误判为短码碰撞，以便系统不会无意义地重复创建请求。
13. 作为访问者，我希望按短链接原有路径访问新短码，以便继续获得 302 跳转。
14. 作为访问者，我希望大小写不同的短码被准确区分，以便访问的始终是对应的原始 URL。
15. 作为访问者，我希望 3 位、9 位或包含非 Base62 字符的路径得到不存在响应，以便短码格式边界明确。
16. 作为访问者，我希望不存在、已过期和已禁用的短链接保持现有响应语义，以便新生成机制不改变跳转规则。
17. 作为访问者，我希望过期或禁用的短码不会重新分配给新映射，以便旧短链接的含义保持稳定。
18. 作为维护者，我希望完整短码存储在映射表中并有数据库主键兜底，以便跳转查询与唯一性约束直接作用于公开标识。
19. 作为维护者，我希望发号表只负责产生唯一整数，以便发号与建立映射的职责清楚。
20. 作为维护者，我希望映射表首次插入时就带有最终短码，以便数据库始终能约束短码非空。
21. 作为维护者，我希望发号成功但映射失败时保留已发出的 ID 且不复用，以便失败不会破坏后续短码唯一性。
22. 作为维护者，我希望第一次短码主键冲突就留下异常记录，以便即使重试成功也能发现编码或部署配置问题。
23. 作为维护者，我希望多个应用实例使用同一编码规则，以便分布式部署不会因参数不一致产生短码异常。
24. 作为维护者，我希望开发阶段能清理数据并调整编码参数，以便在正式发布前完成验证。
25. 作为维护者，我希望正式发布短链接后规则保持稳定，以便已发布短码继续有效。
26. 作为维护者，我希望知道方案允许空洞和发号表增长，以便能够估计存储开销与失败语义。
27. 作为维护者，我希望能区分并发正确性与创建吞吐，以便在有明确性能目标时再做压测和优化。
28. 作为维护者，我希望编码规则有可复算的边界样例，以便未来修改时能发现不兼容行为。

## Implementation Decisions

- 遵循已接受的阶段 2 ADR。维持创建接口、跳转路径、创建成功响应字段以及不存在、过期、禁用和 302 跳转的既有契约。短码是公开标识，外观混淆不代表防枚举或访问控制。
- 使用一个追加式 MySQL 发号表，其唯一数字 ID 由 `BIGINT AUTO_INCREMENT` 分配。每次创建先插入一条发号记录并提交，取得该次插入生成的 ID。多个应用实例共享一个主写库，不使用 Redis 发号、分布式锁、Snowflake 节点号或时钟回拨处理。
- 发号与建立映射是同一应用中的两个职责，分别提交。发号成功后若应用退出、编码失败或映射插入失败，已发 ID 和发号记录保留，允许空洞，绝不回收或复用；只有映射成功插入后才返回创建成功。
- 映射表继续以完整短码为主键，不增加数字 ID 列。短码列为区分大小写的 `VARCHAR(8) NOT NULL`，首次插入就带有最终短码；跳转直接按存储的短码查询，不从短码反推 ID。
- Base62 字符表固定为 `0123456789abcdefghijklmnopqrstuvwxyzABCDEFGHIJKLMNOPQRSTUVWXYZ`。允许的发号 ID 为 1 至 `62^8`。用固定参数 `a = 134941606358707`、`b = 90439432943237` 对 ID 做模 `62^8` 的仿射双射：将 ID 减一、乘以 `a`、加 `b`，再取模。将结果按字符表编码，不足 4 位时在左侧补 `0`；超过 ID 上限则创建失败，不允许取模复用旧短码。计算须避免整数乘法溢出。
- 固定编码样例包括：ID 1 对应 `pGeGLWSx`，ID 2 对应 `1ZXuEkNa`，ID 23 对应 `G8o4qYn`，最大允许 ID 对应 `NmvSTyXU`。参数与模数互质保证不同允许 ID 不会得到相同短码；数据库主键仍作为实现或配置错误的最终兜底。
- 新方案只在映射表短码主键冲突时重新发一个 ID 并再插入一次，总计最多两次。首次冲突立即记录异常；第二次仍冲突则返回 `500 SHORT_CODE_GENERATION_FAILED`，且不产生新映射。非短码主键冲突、发号失败及其他数据库异常不按碰撞重试，也不在响应中泄露内部信息。
- 跳转校验接受 4 至 8 位 Base62 字符并区分大小写；格式错误与不存在的短码保持原有不存在响应。过期、禁用、原始 URL 保存、创建时间及有效时长规则保持不变。
- 现有页面直接显示服务端返回的短码与完整短链接，复制和打开功能不依赖固定 8 位格式；本阶段不需要改变页面交互契约。
- 开发数据无需保留。实施时更新数据库结构并重建开发数据，不能只依赖已有的“表不存在时创建”脚本来修改旧表。发布需要保留的真实短链接后固定字符表、参数与补齐规则；当前不设计新旧规则共存机制。
- 累计 1000 万映射是评估基线，上亿条是后续容量问题。当前只要求多实例并发创建的正确性，不承诺固定创建 QPS；发号表随已分配 ID 数量增长，具体吞吐与存储由后续压测评估。

## Testing Decisions

- 好的测试从可观察行为出发：给定创建或跳转请求及数据库状态，断言响应、短码格式、持久化映射、发号记录和失败后的状态；不要只复述私有方法的循环次数或实现细节。
- 主要沿用现有基于 MockMvc 与真实 MySQL 的公开接口集成测试，覆盖创建后的跳转、短码主键和大小写语义、独立提交后失败留下的空洞、仅一次的主键冲突重试，以及并发创建时无重复短码。现有创建和跳转接口测试已经提供先例。
- 对独立的纯编码器使用少量单元测试，验证固定样例、ID 为 0、允许 ID 的两端、超出上限的 ID、字符集、4 至 8 位和各长度边界。用互质条件证明双射；随机抽样没有碰撞不能代替该证明。
- 现有服务层的碰撞单元测试与 API 集成测试反映随机短码和四次尝试，实施时应更新或删除这些旧断言，避免同时维护两套互相冲突的预期。
- 测试 3 位、9 位、非法字符和大小写不同的跳转路径，并回归永久、过期、禁用以及相同原始 URL 多次创建的行为。并发测试验证唯一性，不将单次测试结果当作生产 QPS 承诺。
- 测试环境使用真实 MySQL；API 集成测试不依赖发号表从 1 开始或 ID 连续，因为自增值可因失败及其他测试而出现空洞。

## Out of Scope

- 将发号模块拆成独立微服务、使用 Redis 或 Snowflake 发号、处理 Snowflake 时钟回拨，以及多主写数据库同时接受创建。
- 把短码作为访问凭据、保证不可枚举、增加随机后缀、限流或反爬策略。
- 现在就实现 Redis 跳转缓存、访问统计、用户系统、自定义短码或创建请求幂等键。
- 对已有正式短链接进行迁移，或在已有正式数据上同时运行不同版本的编码规则。
- 在没有明确创建吞吐和延迟目标时引入号段缓存，或承诺上亿条数据下的固定性能。
