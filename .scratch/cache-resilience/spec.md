# 阶段 4：缓存穿透与缓存异常场景

## Problem Statement

短链接跳转已经使用 Redis Cache Aside，但当前只有可跳转映射进入缓存。对于格式合法、却不存在的短码，每次访问都会在 Redis miss 后查询 MySQL；已过期和已禁用映射也会反复回源。热门短码首次访问或缓存到期时，同一时刻的多个请求可能重复查库。

直接增加一个空值标记无法完整解决问题：不存在、已过期、已禁用需要保持不同业务语义；迟到的旧查询可能在新建或重新启用完成后回填旧拒绝结果；共享旧加载任务也可能让新请求继续获得旧结果。Redis 操作超时后，还需要区分数据库变更已提交与整次操作是否已经完成。

项目目标是一个能够说明取舍、验证正确性的 Java 后端实习项目。需要减少同一码重复访问和实例内并发回源，同时保留明确的故障边界，不模拟互联网亿级流量，不承诺挡住持续更换合法短码的扫描。

## Solution

依据已接受的阶段 4 架构决策，在原有 Cache Aside 上增加三类跳转拒绝结果缓存、向下 TTL 抖动、缓存版本校验及每实例内的请求合并。MySQL 继续作为权威数据源。

不存在、已禁用、已过期分别维持 404、403、410，缓存 TTL 上限默认分别为 30 秒、15 秒、5 分钟。写缓存时随机缩短配置时长的 0%～10%，命中不续期；业务过期仍逐次检查。永久映射正缓存上限仍为 5 分钟，限时正缓存不得超过业务剩余有效时长。

操作完成要求数据库提交且缓存协调已经确认。通过更换缓存版本并原子校验回填，防止旧查询在操作完成后污染缓存；新请求也不得加入旧版本的加载任务。正常的一轮同码、同版本 miss 在每个实例内共享一次查询；等待上限默认 200 毫秒，超时后重读一次缓存，仍 miss 就独立查 MySQL。

创建映射已经提交但缓存协调未确认时，返回专门的 503 部分完成响应和已保存短码。维护者按原短码仅恢复缓存协调，不重新创建映射。暂不实现 Bloom Filter、跨实例互斥回源及其他大型流量治理机制。

## User Stories

1. 作为短链接访问者，我希望有效短链接继续返回 302 和正确的原始 URL，以便现有跳转行为保持稳定。
2. 作为短链接访问者，我希望非法格式短码直接被拒绝，以便无效请求不占用缓存和数据库资源。
3. 作为短链接访问者，我希望大小写不同的短码仍被精确区分，以便访问正确的短链接映射。
4. 作为系统维护者，我希望重复访问同一个不存在短码时复用 404 缓存，以便减少重复数据库查询。
5. 作为短链接访问者，我希望不存在、已过期和已禁用仍分别返回 404、410 和 403，以便准确理解无法跳转的原因。
6. 作为系统维护者，我希望已禁用结果也能被短时间缓存，以便反复访问已禁用映射时减少回源。
7. 作为系统维护者，我希望已过期结果能被缓存，以便永久不能通过当前有效期检查的映射不被反复查询。
8. 作为短链接访问者，我希望已禁用映射在到期当刻返回 410，以便缓存寿命不会覆盖业务有效期。
9. 作为短链接访问者，我希望有效映射在业务到期后停止跳转，以便等待查询结果期间也不会放行已经过期的映射。
10. 作为系统维护者，我希望三类拒绝结果的 TTL 分别可配置，以便根据状态稳定性调整缓存寿命。
11. 作为系统维护者，我希望缓存命中不延长 TTL，以便持续访问不会让旧结果永久存留。
12. 作为系统维护者，我希望写入缓存时采用小幅向下 TTL 抖动，以便分散部分集中到期且不增加已确认的缓存上限。
13. 作为系统维护者，我希望每个缓存条目都有有限寿命，以便不存在短码和协调占位不会永久积累。
14. 作为短链接访问者，我希望缓存自然到期后重新查询当前映射，以便访问结果仍随权威数据更新。
15. 作为系统维护者，我希望同一码同版本的并发 miss 在一个实例内共享查询，以便减少缓存击穿产生的瞬时回源。
16. 作为短链接访问者，我希望不同短码能够同时加载，以便一个慢短码不会阻塞其他短码。
17. 作为系统维护者，我希望不同实例各自拥有请求合并状态，以便明确实例内合并与跨实例一致性的不同保证。
18. 作为短链接访问者，我希望等待共享任务有明确上限，以便不会无限等待另一个请求。
19. 作为短链接访问者，我希望等待超时后能够重新检查缓存并独立回源，以便在允许重复查询的前提下继续得到业务结果。
20. 作为短链接访问者，我希望一个等待者超时不取消共享任务，以便其他仍在等待的请求不被连带中断。
21. 作为系统维护者，我希望加载成功或失败后清理任务，以便后续请求可以重新加载而不积累无用任务。
22. 作为短链接访问者，我希望数据库读取失败保持服务错误，以便数据库故障不会被误报成短码不存在。
23. 作为短链接访问者，我希望 Redis 暂时不可达时回源 MySQL，以便缓存故障不直接决定业务结果。
24. 作为短链接访问者，我希望缓存回填失败时仍能获得已经读到的 MySQL 结果，以便跳转读取保持原有降级语义。
25. 作为系统维护者，我希望损坏或未知格式的缓存被忽略并重新加载，以便坏数据不会变成错误的 404 或跳转地址。
26. 作为短链接访问者，我希望无业务结果的协调占位只表示尚需加载，以便它不会被误认为映射不存在。
27. 作为短链接创建者，我希望收到创建完成响应后，新开始的访问不会因为旧 404 缓存被拒绝，以便新短链接能够按当前状态使用。
28. 作为系统维护者，我希望重新启用完成后，新开始的请求不再因旧 403 缓存被拒绝，以便状态恢复具有明确完成含义。
29. 作为系统维护者，我希望迟到的旧查询不能覆盖新缓存版本，以便创建或状态维护后的可见性不依赖等待 TTL 到期。
30. 作为短链接访问者，我希望新版本请求不复用旧版本加载结果，以便缓存写入被拒绝后仍不会通过共享任务收到旧拒绝结果。
31. 作为系统维护者，我希望条目过期或被淘汰后不能复用旧版本，以便旧任务不能在条目丢失后重新污染缓存。
32. 作为系统维护者，我希望多个实例共享同一 MySQL 主写库和 Redis 时遵守同一协调协议，以便一致性不依赖进程内锁或全局静态变量。
33. 作为系统维护者，我希望明确区分数据库提交与维护完成，以便直接 SQL 提交后仍会执行受控的缓存协调步骤。
34. 作为短链接创建者，我希望部分完成响应明确提供已保存短码和协调未确认说明，以便避免把已经入库的映射当成完全没有创建。
35. 作为系统维护者，我希望按已保存短码只重试协调，以便恢复不会再次发号、插入映射或覆盖后续启用状态。
36. 作为系统维护者，我希望协调已经执行但响应超时后仍能安全重试，以便结果不确定的 Redis 超时可以恢复。
37. 作为系统维护者，我希望数据库创建未确认时不宣称已经创建，以便部分完成响应具有可信含义。
38. 作为系统维护者，我希望 Redis 重启或恢复旧数据后先停用旧缓存并清理，以便缓存和版本整体回滚不会被误当作正常协调状态。
39. 作为项目实现者，我希望查询次数、到期边界、并发顺序和部分完成恢复都有可重复的验收测试，以便能够用证据解释缓存方案。
40. 作为项目讲解者，我希望文档明确 Bloom Filter、热点 Key 和雪崩方案的取舍，以便说明当前项目解决的实际问题及尚未承诺的能力。

## Implementation Decisions

### 现有模块与职责

- 复用现有短链接服务作为业务入口，扩展创建与跳转读取流程；控制器保持已有 URL 校验、创建和跳转契约，仅为已提交创建的协调未确认增加专门错误响应。
- 扩展现有 RedirectCache 抽象及 Redis 适配器，使其能够表达缓存未命中、协调占位和各类业务结果，并提供版本初始化、带版本的条件回填及变更协调能力。原先只表达正值或 miss 的接口不足以覆盖新语义。
- 实例内请求合并放在应用服务的加载职责中，由每个实例独立持有。合并只管理正在进行的查询，不作为长期本地缓存。
- 内部维护能力支持数据库状态调整后的受控协调及按短码恢复协调，不增加公开的启用、禁用、删除或恢复 API。
- MySQL 映射表、发号表及短码生成机制沿用现状。本阶段不增加幂等键、创建请求表或持久化协调任务表。

### 缓存结果与业务语义

- 格式校验仍为 4 至 8 位大小写字母和数字，保持大小写；失败时按现有规则返回 404，不读取 Redis、MySQL 或合并任务。
- MySQL 成功查询后先判断映射是否存在，再判断是否过期，最后判断是否禁用。不存在、已过期、未过期但已禁用分别返回 LINK_NOT_FOUND、LINK_EXPIRED、LINK_DISABLED；HTTP 状态分别为 404、410、403。
- Redis 仅保存跳转或拒绝判断所需信息，不保存完整数据库实体。可跳转结果包含原始 URL 和业务过期时间；已禁用结果保留业务过期时间，以便命中时判断是否已转为过期。
- 协调占位没有业务结果，必须走加载流程。缓存不存在、占位存在、业务映射不存在是三个不同概念，不能共用一种空值表达。
- 可跳转和已禁用快照都由每个请求在使用时重新检查业务过期；到期当刻及之后返回 410。共享的是用于判断的快照，不能让等待者无条件沿用加载者较早计算的 302 或 403。
- 数据库查询失败不产生拒绝结果缓存，保持现有 500 语义。缓存读写异常、未知结果类型、错误字段或无法解析的时间都不能推导出映射不存在。
- 有效跳转保持 302、正确 Location 及 Cache-Control: no-store；业务错误和新增的部分完成错误同样不允许 HTTP 缓存。

### TTL 与配置

| 缓存结果 | 默认配置上限 | 写入时的实际配置范围 |
| --- | --- | --- |
| 不存在 | 30 秒 | 27～30 秒 |
| 已禁用 | 15 秒 | 13.5～15 秒 |
| 已过期 | 5 分钟 | 270～300 秒 |
| 永久映射正值 | 5 分钟 | 270～300 秒 |
| 限时映射正值 | 5 分钟 | 抖动后的配置 TTL 与业务剩余有效时长取较小值 |

- 三类拒绝结果的 TTL、正值 TTL 和合并等待预算分别可配置。所有配置必须能够形成正且有限的时长。
- 每次业务结果写入时随机缩短配置 TTL 的 0%～10%，不向上抖动；缓存命中不续期。限时正值的剩余有效时长不大于零或不能形成正的毫秒 TTL 时，不回填为可跳转结果。
- 缓存值与 TTL 同步写入，不能先写值再单独设置过期。业务有效期由应用判断，不能仅依靠 Redis TTL。
- 无业务结果的版本占位也必须具有正且有限的 TTL；它不是永久保存的历史短码集合。占位过期只影响回填是否能够成功，不能据此返回 404。

### 版本与操作完成

- 新缓存格式携带版本标识和明确结果类型，使用新的格式版本隔离阶段 3 的两字段结构。所有参与一致性保证的实例使用同一协议。
- 对实际 miss 或仅有协调占位的读取，取得该短码当前版本后再查询 MySQL。回填原子校验版本仍相同，才同时写入业务结果与 TTL；校验失败应放弃该次回填，不无条件覆盖新条目。
- 版本及业务结果在同一个有限 TTL 的条目中。条目丢失时旧版本条件回填失败；重新初始化必须使用新版本，不能在 TTL 到期或淘汰后复用旧版本。
- 所有业务结果更新都遵守版本协议，包括可跳转、三类拒绝结果，以及业务过期产生的结果更新。初始化、条件回填和版本更换也不能通过非原子的检查后写入绕过协议。
- 创建和启用状态维护在数据库确认提交后更换缓存版本并清除旧业务结果。这里可以留下无结果占位，不预热原始 URL；确认缓存协调成功后才报告操作完成。
- 操作完成之后才开始的请求不能因为操作之前的缓存或共享任务读到旧拒绝结果。与变更重叠的旧请求允许按此前快照完成；后续新的合法状态变更和自然过期继续生效。
- 多实例共享同一个 MySQL 主写库及 Redis。协议不把 MySQL 与 Redis 变成一个原子事务，不依赖 JVM 内互斥来宣称跨实例一致性。
- 任意绕过流程的直接 SQL 不属于完成保证。维护可以保留 SQL 步骤，但数据库提交后还须执行受控协调，分别报告数据库变更与操作完成。

### 实例内请求合并与超时

- 合并键为短码和当前版本。在无变更、无等待超时、无条目丢失且正常回源的一轮并发 miss 中，每个实例由一个加载者查 MySQL，其他同版本请求共享其结果。
- 不同短码能够并行加载；不同版本必须拥有不同任务。不同实例允许各回源一次，不实现 Redis 锁来合并跨实例回源。
- 等待共享任务的上限默认 200 毫秒，可配置。超时后只重读一次缓存，仍 miss 则独立查 MySQL，允许重复回源；不无限循环重新加入原任务，不因等待者超时取消共享任务。
- 200 毫秒仅为等待共享任务的预算，不是 HTTP 总耗时上限，也不代替数据库查询超时。任务成功或失败后清理对应登记；数据库失败保持 500，后续请求可以重新加载。
- Redis 版本无法确认时直接按权威数据回源，不复用可能在变更前开始的共享任务；没有有效版本依据时不得无条件回填。
- 缓存读取失败继续回源，读取路径的回填失败不覆盖已读到的 MySQL 业务结果。读取降级与变更协调失败的完成语义必须区分。

### 已提交创建的部分完成与恢复

- 数据库创建确认提交且已知短码，但随后缓存协调失败或超时时，返回 HTTP 503 专门响应。响应必须具有明确的错误标识、说明及 shortCode；说明明确数据库创建已提交、缓存协调未确认，不声称已回滚。
- 普通创建完成仍使用现有 201 及创建响应；数据库创建失败或提交状态未确认时，沿用现有错误语义，不伪造已提交创建的部分完成结果。
- 为协调未确认记录可按短码定位的错误日志。Redis 超时可能意味着操作已执行但未收到确认，不能把未确认表述为确定未执行。
- 维护者通过受控的内部入口按同一 shortCode 只重试版本更新与结果清除。恢复不重新发号、不再次插入映射、不按旧请求重写 enabled；重新启用的恢复同样仅重试协调。
- 多次协调恢复必须安全，协调确认后才报告完成。恢复记录依赖已有短码和日志，不引入新的持久化任务系统。
- 客户端请求幂等不在范围内。网络响应完全丢失后，再次 POST 仍可能创建另一条映射；相同原始 URL 可对应多条独立映射的既有语义不变。

### 故障边界、雪崩和热点 Key

- 即时可见保证适用于同一 Redis 主实例、已确认协调更新未丢失的运行过程；暂时不可达时读取回源 MySQL，变更协调未确认则不报告完成。
- Redis 重启、恢复旧备份或切换实例时，先停用旧缓存，完成清理重建后再恢复缓存使用。缓存结果和版本可能一起回滚，因此不承诺在确认写入丢失或自动故障切换后自动保持即时可见。
- TTL 抖动缓解部分集中到期；实例内合并缓解同码并发 miss。Redis 整体不可用时仍可能出现大量回源，不承诺数据库能够承担全部请求。
- 保留现有短 Redis 超时和错误日志，关注访问量、请求延迟、回源次数、Redis 超时和缓存内存。本阶段不要求新增监控平台或性能指标承诺。
- 持续更换合法但不存在短码仍可能每个新码查库并写新条目。短 TTL 不等于严格内存上限或限流；正常命中下的 Redis 热点压力也不由请求合并解决。

## Testing Decisions

### 测试入口与已有实践

- 测试边界沿用用户已确认的阶段 4 验收设计：以短链接服务公开行为为主要入口，再以现有 HTTP 入口连接真实 MySQL 和 Redis 验证协议。无需再次采访确认，也不为每个私有方法新增独立测试入口。
- 优先扩展现有短链接服务测试实践：可控 Clock、缓存替身、持久层查询计数，以及可控制的查询完成时点。需要可控随机源验证抖动端点，新增可测性能力尽量收敛在既有缓存与加载边界。
- 优先扩展现有 MockMvc 与 Testcontainers 集成测试实践：真实 MySQL／Redis、Mapper spy、HTTP 状态和响应字段、Redis 值与实际 TTL。现有“仅可跳转结果缓存”“创建完全没有缓存 Key”等阶段 3 断言需要按新协议重新评估，协调占位不等于预热可跳转结果。
- 好的测试观察业务结果、查询次数、写入后的期限、操作完成后的可见性及恢复副作用；不能靠多个相同 302 响应推断缓存命中或并发合并。不要通过私有函数、集合类型、锁实现或 Lua 文本的逐字匹配验证实现细节。

### 行为验收

1. 格式非法返回现有 404，Redis、MySQL 和合并任务都不被调用；大小写不同短码维持不同映射。
2. 对不存在、已禁用和已过期分别验证首次 miss 查询后回填、后续命中返回对应状态且没有新增 SQL；缓存自然到期后重新加载当前结果。
3. 回归正值 hit／miss、原始 URL、302、Location、no-store，永久与限时映射维持既有语义。
4. 使用可控时钟覆盖业务到期前、到期当刻及之后；缓存命中和等待共享结果期间到期均正确转为 410，过期优先于禁用。
5. 使用可控随机输入验证 0% 和 10% 端点、各 TTL 范围、命中不续期以及限时正值的剩余有效时长上限。真实 TTL 断言为执行耗时留合理余量，不用随机分布抽样证明抖动正确。
6. 协调占位只导致加载，不返回 404；所有结果和占位具有有限正 TTL。条目过期或被淘汰后，旧任务不能恢复旧版本或无条件回填。
7. 用同步点控制一轮同码同版本请求交叠，正常条件下每实例仅一次 SQL；不同短码可以同时进入数据库查询，不被全局锁串行化。404、403、410 的加载同样适用。
8. 等待者超时后重读缓存或独立回源，允许查询次数增加；不取消共享任务，不无限重试等待。任务成功或失败后清理，后续请求可以正常重试。
9. 在旧 MySQL 查询完成后暂停，创建或重新启用并完成协调，再恢复旧回填。真实 Redis 的版本条件阻止旧结果写入，完成后才开始的请求使用新版本。
10. 专门验证新版本请求不加入旧任务，而不只验证 Redis 最终没有旧值；旧请求按快照完成的允许边界与新请求的保证必须分别断言。
11. 独立应用实例共享 MySQL／Redis，验证版本协调跨实例生效；每实例各回源一次是允许结果。至少一项关键验证使用独立进程或等效实例隔离，避免误把静态任务表当作分布式机制。
12. 缓存读取失败、超时、回填失败、损坏数据和未知格式按既定语义处理，不能变成错误 404。数据库查询失败仍为 500，不产生负缓存；版本无法确认时不共享旧任务或无条件回填。
13. 用少量真实 Redis 断连或超时验证降级。数据库已经提交后注入创建协调失败，验证 503、shortCode 和未确认说明；普通数据库创建失败不产生该部分完成响应。
14. 按原短码恢复协调，断言映射数量、发号次数不增加，enabled 不被旧恢复步骤重写；协调已执行但响应超时后重复恢复仍安全。
15. 以受控步骤停用旧缓存、清理后恢复按需加载，验证新的运行过程；不把直接加载旧快照的结果当作自动维持即时可见。
16. 用少量确定的不同无效短码验证每个新码仍可能回源且条目有有限 TTL，明确方案边界，不宣称抗攻击能力或目标 QPS。

- 并发先后使用闩锁等同步点控制，等待测试使用可控预算及有界等待，不用长时间 sleep 代替同步。真实 TTL 自然到期可缩短测试配置，以有界轮询验证。
- 容器测试隔离数据库、Redis 条目与应用任务状态。与新缓存格式有关的断言使用外部协议及序列化契约，不沿用旧结构的两字段断言。
- 本轮只生成规格；上述测试在后续实现阶段执行，不宣称当前代码已通过阶段 4 验收。

## Out of Scope

- Bloom Filter、Counting Bloom Filter、Cuckoo Filter 的实现及其专门测试。文档理解空间收益、误判、新增同步和删除限制即可。
- 持续更换短码扫描的全面防护、严格缓存内存上限、全局数据库限流或任意故障下全局只查询一次的保证。
- Redis 分布式锁、Redlock、跨实例请求合并、后台异步刷新、逻辑过期、自动预热、专门限流或熔断。
- Redis Sentinel／Cluster、自动故障切换及丢失确认写入或恢复旧快照后的自动强一致。
- 长期本地缓存、热点 Key 拆分、专门热点节点和新的监控平台。
- 修改短码生成或持久化模式、增加请求幂等键、持久化创建恢复表、自动恢复任务队列。
- 新的公开启用、禁用、删除、修改原始 URL、修改有效期或恢复 API。
- 超出共享同一 MySQL 主写库与 Redis 的部署拓扑、多独立数据库写入，以及亿级流量或固定 QPS／延迟承诺。
- 本轮的任务拆分、编码、部署和实现测试执行；本次只发布实施规格。

- 版本校验承担一致性职责，实例内请求合并承担减少同码并发回源职责，TTL 抖动承担分散集中到期职责；不能将一个机制解释为已经解决其他全部缓存异常。
- 空值缓存足以覆盖本阶段的同码重复查询目标，但这里必须是有业务含义的拒绝结果，不能只是无法区分原因的空字符串。它不能挡住每次更换短码的扫描。
- Bloom Filter 的“可能存在”误判只让无效短码继续查询，不能据此跳转。普通 Bloom Filter 不能安全清除单成员共享位；未来删除映射可保留历史成员由 MySQL 判定不存在，必要时重建过滤器。当前不新增删除能力。
- 即时可见、503 部分完成及恢复流程是用户明确选择的完成契约，由这一契约带来的版本协议不能被仅提交后 DEL、延迟双删或有限 TTL 兜底替代。
