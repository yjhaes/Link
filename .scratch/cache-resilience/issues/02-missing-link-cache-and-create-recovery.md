# 02: 不存在短码复用 404，创建完成后立即可访问

**What to build:** 重复访问同一个不存在短码复用 404 缓存；该短码随后创建并完成协调后，新开始的请求可按新映射使用。数据库已经创建但协调未确认时，创建者得到可恢复的部分完成结果。

## Acceptance criteria

- [x] 成功查询确认为不存在后写入独立 404 结果，TTL 上限默认 30 秒，实际抖动为 27～30 秒；后续命中不查 MySQL，命中不续期。
- [x] 新建映射数据库确认提交后更换缓存版本并清除旧结果，协调确认后返回现有 201；允许留下有限 TTL 占位，不预热原始 URL。
- [x] 数据库确认提交后协调失败或超时返回专门 503，携带 shortCode 和“数据库创建已提交、缓存协调未确认”说明，并记录可按短码定位的日志；数据库失败或提交未确认不冒充该结果。
- [x] 提供受控的内部按短码协调恢复能力，多次执行安全；不重新发号、不再次插入映射、不按旧请求重写启用状态。
- [x] 用同步点暂停旧查询，在创建并完成协调后恢复回填；旧 404 因版本不匹配被拒绝，完成后才开始的新请求能够按新映射使用。
- [x] 通过独立实例及真实 Redis／MySQL 验证创建协调跨实例生效，不依赖 JVM 内锁或静态状态；旧重叠请求按此前快照完成的允许边界与新请求的保证分别断言。
- [x] HTTP 验证首次 miss、后续 404 hit、普通创建成功、503 部分完成及恢复；恢复时映射数量和发号次数不增加。
- [x] 覆盖 Redis 协调已执行但响应超时后的安全重复恢复；网络响应完全丢失后重复 POST 不宣称具有请求幂等能力。
- [x] 少量不同无效短码仍可每个新码查库，缓存条目有有限 TTL；数据库查询失败保持 500，不能写入 404 缓存。

## Comments

- 按用户确认的阶段 4 拆分发布。依赖 01 的版本化结果、条件回填及变更协调能力；本任务交付的内部恢复能力由 04 复用。

## Answer

- 基于最新主分支 `21550c2`（已合并任务 01）接入独立 NOT_FOUND 缓存，默认 TTL 上限 30 秒、向下抖动 0%～10%，命中不续期且不查询 MySQL；查询失败不写负缓存。
- 创建入口挂起调用者事务，MyBatis 非事务插入确认提交后轮换缓存版本，成功才返回 201。协调失败或超时返回 `503 CREATE_CACHE_COORDINATION_UNCONFIRMED`，包含已保存短码和提交已确认／协调未确认说明，日志可按短码定位；网页也显示该部分完成结果。
- 内部 `ShortLinkService.recoverCacheCoordination` 按同一短码仅重试协调，重复执行安全；不重新发号、插入映射或改写启用状态。README 维护流程已统一使用该受控入口，未增加公开恢复 API。
- 独立 Spring 应用上下文共享真实 MySQL／Redis，使用闩锁暂停旧 SQL 查询快照，证明创建确认后开始的新请求可跳转、旧重叠请求允许返回 404、旧版本回填被拒绝。恢复测试覆盖 Redis 已执行但响应超时、映射及发号数量不增加、禁用状态保持，以及重复 POST 仍会产生独立映射的边界。
