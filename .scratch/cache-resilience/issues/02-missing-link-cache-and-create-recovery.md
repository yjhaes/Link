# 02: 不存在短码复用 404，创建完成后立即可访问

**What to build:** 重复访问同一个不存在短码复用 404 缓存；该短码随后创建并完成协调后，新开始的请求可按新映射使用。数据库已经创建但协调未确认时，创建者得到可恢复的部分完成结果。

## Acceptance criteria

- [ ] 成功查询确认为不存在后写入独立 404 结果，TTL 上限默认 30 秒，实际抖动为 27～30 秒；后续命中不查 MySQL，命中不续期。
- [ ] 新建映射数据库确认提交后更换缓存版本并清除旧结果，协调确认后返回现有 201；允许留下有限 TTL 占位，不预热原始 URL。
- [ ] 数据库确认提交后协调失败或超时返回专门 503，携带 shortCode 和“数据库创建已提交、缓存协调未确认”说明，并记录可按短码定位的日志；数据库失败或提交未确认不冒充该结果。
- [ ] 提供受控的内部按短码协调恢复能力，多次执行安全；不重新发号、不再次插入映射、不按旧请求重写启用状态。
- [ ] 用同步点暂停旧查询，在创建并完成协调后恢复回填；旧 404 因版本不匹配被拒绝，完成后才开始的新请求能够按新映射使用。
- [ ] 通过独立实例及真实 Redis／MySQL 验证创建协调跨实例生效，不依赖 JVM 内锁或静态状态；旧重叠请求按此前快照完成的允许边界与新请求的保证分别断言。
- [ ] HTTP 验证首次 miss、后续 404 hit、普通创建成功、503 部分完成及恢复；恢复时映射数量和发号次数不增加。
- [ ] 覆盖 Redis 协调已执行但响应超时后的安全重复恢复；网络响应完全丢失后重复 POST 不宣称具有请求幂等能力。
- [ ] 少量不同无效短码仍可每个新码查库，缓存条目有有限 TTL；数据库查询失败保持 500，不能写入 404 缓存。
