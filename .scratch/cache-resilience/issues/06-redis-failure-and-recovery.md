# 06: Redis 中断与旧数据恢复后保持正确跳转

**What to build:** Redis 临时不可达时访问者仍能按 MySQL 结果跳转或得到正确拒绝原因；维护者在 Redis 重启、切换或恢复旧数据后，通过受控清理恢复按需缓存，明确即时可见的保证边界。

## Acceptance criteria

- [ ] 在版本协议与实例内请求合并已接入的完整流程中，以少量真实 Redis 断连或超时验证正确回源，不将缓存异常误报为 404。
- [ ] 版本无法确认时不加入可能在变更前开始的共享任务，不无条件回填；读取路径回填失败不改变 MySQL 结果，变更协调未确认不报告操作完成。
- [ ] 损坏或未知结构、错误时间与未知业务结果类型按既定 miss／降级语义处理，不产生错误跳转或错误拒绝。
- [ ] 提供并验证受控的停用旧缓存、清理旧格式或旧数据、恢复按需加载流程，覆盖旧缓存结果与旧版本整体恢复的场景。
- [ ] 恢复说明明确同一 Redis 主实例、已确认协调更新未丢失的保证前提；自动故障切换或旧快照恢复未经清理不能宣称保持即时可见。
- [ ] 保留现有短 Redis 超时和可按短码定位的错误日志，说明 TTL 抖动、实例内合并、整体不可用及正常命中热点压力的不同边界。
- [ ] 使用有限数据验证不断更换无效短码仍可能回源、缓存及占位均有有限 TTL；不承诺严格内存上限、抗攻击能力、目标 QPS 或任意故障下全局只查一次。
- [ ] 文档保留已确认的不实现范围：Bloom Filter、跨实例互斥回源、长期本地缓存、热点拆分、预热、后台刷新、专门限流／熔断、Sentinel／Cluster及新的监控平台。
- [ ] 本任务以受控恢复的可演示行为为交付；其他任务的常规业务和并发测试仍随各任务验收，不集中留到本任务才执行。
