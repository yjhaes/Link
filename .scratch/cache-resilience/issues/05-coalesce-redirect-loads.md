**What to build:** 对已经具备全部业务结果的跳转流程，正常的一轮同码同版本 miss 在每个实例内共享一次 SQL；不同码并行，等待超时的请求可以继续读取权威数据。

## Acceptance criteria

- [x] 合并键为短码和当前版本，每个实例独立持有正在进行的任务；不使用长期本地缓存、JVM 全局任务表或跨实例 Redis 锁来改变已确认的保证范围。
- [x] 在无变更、无等待超时、无条目丢失且正常回源的一轮交叠请求中，各实例同码同版本只查一次；可跳转、404、403、410 都适用。
- [x] 不同短码可以同时进入数据库查询，没有用一个全局锁串行化。
- [x] 新版本请求不能加入旧版本任务，创建／重新启用完成后才开始的请求不得获得旧任务的 404 或 403；测试不只检查 Redis 的最终值。
- [x] 默认等待上限为可配置的 200 毫秒；等待者超时后重读一次缓存，仍 miss 则独立 SQL，允许重复回源，不无限重新加入原任务。
- [x] 一个等待者超时不取消或异常完成其他请求仍使用的共享任务；200 毫秒仅为等待预算，不被描述为 HTTP 总耗时上限。

- [x] 加载成功或失败后清理对应任务；数据库失败保持 500 且不产生拒绝缓存，后续请求可以重试。
- [x] 用可控同步点和查询计数验证合并、不同码并行、新旧任务隔离、等待超时及任务清理；至少一项关键验证使用独立实例／进程隔离，明确不同实例允许各回源一次。
- [x] Redis 版本无法确认时不复用可能跨越变更的共享任务，不无条件回填；相应完整故障恢复验证与 06 的流程相衔接。
