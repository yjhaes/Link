# 06: 停采后保留历史查询并持续清理过期日志

**What to build:** 维护者停止采集时仍能查询窗口内已保存的统计；旧访问日志在启动、每日和积压维护轮次中持续按预算清理。严格30日查询窗口与故障期间可能延迟的物理删除明确区分。

**依赖说明：** 04 — 管理者查询日期范围 PV/UV 与日趋势

## Acceptance criteria

- [ ] 启动后和每天上海时间00:10清理窗口外日志，按stat_date/id索引每批最多1000行、每批独立提交，不形成一个长期删除事务。
- [ ] 每轮预算30秒，积压每15分钟继续；无清理容量或失败时该轮不反复重试，保留可观察积压和最旧日期，后续轮次追赶。
- [ ] 清理准入容量1并使用统计池与其语句/锁超时，正常释放容量；轮次预算不声称可强制中断任意阻塞SQL。
- [ ] 关闭采集仍运行旧日志清理，不要求HMAC密钥；停机期间不声称清理，恢复启动从过期条件继续，不依赖内存游标或新增持久任务表。
- [ ] 多实例重复清理安全，不新增分布式锁；不会删除有效窗口日志、核心映射或发号数据。
- [ ] 无论物理删除是否完成，04聚合都拒绝超窗查询；停采仍可查有效历史并标明当前不采集，正常GET不再写日志或Cookie。
- [ ] 可控时钟、受控调度与真实MySQL验证窗口首尾、批量提交、预算、失败、无容量、多实例、关闭采集及停机后追赶；通过受保护聚合与持久化结果验证完整生命周期。
- [ ] 更新部署说明中的采集开关、令牌/HMAC配置、池/超时初值、清理积压和备份边界；不自动删除备份/binlog，不宣称物理30日硬期限或无限期事件去重。
- [ ] 不引入异步访问处理或历史补采，已有正常采集、聚合、状态管理与缓存行为回归保持。
