# 03: 统计繁忙与故障可观察，正常跳转继续完成

**What to build:** 在统计容量不足、连接/SQL 失败或数据库已经保存但确认丢失时，访问者仍完成已确定的正常跳转；维护者可以区分确认保存、繁忙丢弃、失败及不确定结果，并验证统计资源不会永久耗尽或接管核心连接。

**依赖说明：** 02 — 合法跳转同步记录匿名访客访问日志

## Acceptance criteria

- [ ] 记录事件尝试、确认保存、dropped、失败/不确定、耗时及池占用，能够通过内部观测和受控错误类别定位故障；不新增监控平台或公开故障注入 API。
- [ ] 占满写入容量后，其他正常 GET 立即绕过统计而非排队，不取消其他请求的写入；正确释放许可，失败后后续请求可以再次正常记录。
- [ ] 连接/SQL 错误仍保持 302、Location 和 no-store，不写核心映射或 Redis 状态，不在请求内生成新事件重试。
- [ ] 受控“先保存后报错”证明日志至多一条、响应仍302、不武断认定超时未执行；唯一约束错误分类和其他错误继续准确区分。
- [ ] 随机值、摘要或元数据处理失败按既有采集规则跳过/置空，不使用公共默认身份，不泄露原始请求信息。
- [ ] 用少量真实 MySQL 断连、锁等待或受控网络延迟核验各超时实际生效；mock 故障只证明语义，不被用作耗时保证。
- [ ] 在统计连接占用或不可用的受控条件下验证核心创建、发号及状态事务保持核心归属；不据此声称同一 MySQL 硬件得到完全隔离。
- [ ] 指标不以短码/IP/访客作无限增长标签，错误记录无 token、Cookie、完整 IP/Referer 或原始请求头；明确阶段超时不是 HTTP 总墙钟上限。
