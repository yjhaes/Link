# 阶段 8：限流、工程化与最终收尾规格

日期：2026-10-04（Asia/Shanghai）

依据：已确认的 Q1～Q24、阶段 8 最终设计与 ADR-0008。本文最初作为ready-for-agent规格发布；用户随后分批明确授权01～12实施，现全部完成并resolved。以下问题背景和“本轮不开始开发”描述是发布阶段的历史，最终实现及验收以Answer和正式验证入口为准。

## Problem Statement

短链接服务已经完成匿名创建、MySQL 持久化和发号、短码编码、跳转及状态维护、版本化 Redis 缓存、负缓存和实例内加载合并，以及 RabbitMQ 异步访问统计、消费幂等、查询与保留清理。用户希望把项目收尾为别人能够独立运行、适合 GitHub 展示、能够写入 Java 后端实习简历并完整解释的最终版本。

目前没有 HTTP 限流，匿名批量创建会增加持久化数据，持续更换合法短码的扫描仍可能逐码回源。Redis 不可用时，跳转无法取得缓存版本，不参加原有请求合并，会逐请求独立查询 MySQL；已有池配置也没有明确核心资源预算。仅声明缓存可降级不能证明数据库能承受全部流量。

已有日志、运维文档与测试需要补全并整理，而不是重新实现或增加更多技术组件。

当前基础配置还将管理令牌和访客 HMAC 密钥设为相同的已提交默认值，默认开启采集，与文档中的无默认管理秘密、独立密钥及默认关闭采集不一致。最终版本必须修复实际配置并同步说明，避免公开示例成为实际秘密。

## Solution

在现有单应用、单 MySQL、单 Redis、单 RabbitMQ 架构中增加按请求组配置的 Redis + Lua 令牌桶，以及实际跳转数据库加载的每实例并发准入。创建从严、跳转宽松，故障时创建和已授权管理操作在进入业务前关闭准入，跳转保留放行和缓存回源，但受独立回源保护约束。

补充最小 Actuator 分组健康、低基数指标、安全日志、OpenAPI/本地 Swagger UI及错误提示，保留核心业务和 best-effort 统计的既有契约。

最终整理精简 README、架构图、演示和正式验证证据，使实际能力、设计取舍和局限都能被复现和解释。

目标是基础防刷和资源保护，不是完整反滥用平台或生产高可用系统。

## User Stories

1. 作为项目使用者，我希望克隆仓库后通过明确步骤初始化并运行全部组件，以便不依赖作者的私人环境。
2. 作为项目使用者，我希望首次生成本地配置后即可构建启动全栈，以便不必手工粘贴数据库和 MQ 初始化命令。
3. 作为项目使用者，我希望普通重启保留映射、访问日志和 broker 状态，以便演示不会因重启丢失持久数据。
4. 作为项目维护者，我希望普通重启、秘密轮换和数据重置分别说明，以便不会误删已有数据或队列积压。
5. 作为匿名创建者，我希望继续创建永久和限时短链接，以便工程化收尾不引入账号门槛。
6. 作为匿名创建者，我希望正常低频创建不被跳转流量抢占额度，以便不同业务操作相互隔离。
7. 作为匿名创建者，我希望过快创建收到明确的 429 和重试提示，以便知道需要等待而不是不断重试。
8. 作为匿名创建者，我希望限流判断失败时在发号和写库前被拒绝，以便不会误认为请求已经创建映射。
9. 作为匿名创建者，我希望响应能区分业务未开始和数据库已提交的 503，以便不会用重复创建代替缓存协调恢复。
10. 作为短链接访问者，我希望跳转额度比创建宽松，以便正常访问不会被写入防刷策略频繁误伤。
11. 作为短链接访问者，我希望热门短码不因所有访问者共享一个桶而被整体封锁，以便多人正常访问仍有合理机会。
12. 作为短链接访问者，我希望同一 IP 跨短码共享跳转额度，以便持续换码扫描不能绕开该 IP 的基础防护。
13. 作为短链接访问者，我希望 GET 和 HEAD 使用同一跳转额度，以便请求方法不能成为额度绕过途径。
14. 作为短链接访问者，我希望 Redis 限流故障时仍能进入原有跳转流程，以便非权威存储故障不立即阻断全部跳转。
15. 作为项目维护者，我希望 Redis 故障回源和正常 miss 都有有限实际查询并发，以便数据库不会被无限同时加载。
16. 作为短链接访问者，我希望回源容量不足时立即收到明确 503，以便不会进入新增的无界等待队列。
17. 作为短链接访问者，我希望缓存命中和等待共享加载不占用额外查询许可，以便保护实际数据库工作而非重复计算请求数。
18. 作为内部管理者，我希望管理令牌鉴权仍先于参数解析和限流依赖，以便未授权请求继续按既有规则拒绝。
19. 作为内部管理者，我希望状态修改和统计查询使用分别配置的管理额度，以便查询不会抢占写入额度。
20. 作为内部管理者，我希望统计与访问明细查询共享管理查询额度，以便两个入口不会叠加绕开保护。
21. 作为内部管理者，我希望管理秘密未配置时接口继续关闭，以便默认运行不意外暴露管理能力。
22. 作为匿名访客，我希望限流拒绝不设置统计 Cookie、不生成访问事件，以便未作出跳转决定的请求不会被当作访问。
23. 作为内部管理者，我希望限流和回源保护拒绝不计 PV/UV，以便统计仍以已记录的正常 GET 访问事件为依据。
24. 作为内部管理者，我希望 HEAD、过期、禁用、不存在及正常跳转的既有口径保持，以便本阶段不会暗中修改历史统计含义。
25. 作为项目维护者，我希望多个应用上下文共享 Redis 时仍共享同一桶额度，以便未来多实例不会因本地计数各自放行。
26. 作为项目维护者，我希望并发竞争最后一个令牌时只有符合额度的请求获准，以便限流检查和扣减没有竞态。
27. 作为项目维护者，我希望闲置限流状态自动清理而不提前重置额度，以便状态生命周期与桶规则一致。
28. 作为项目维护者，我希望脚本缓存丢失可以恢复，而扣减超时不被盲目重试，以便恢复和不确定执行采用不同处理。
29. 作为项目维护者，我希望 Redis 内存有明确预算及满时语义，以便有限 TTL 不被误解为内存硬上限。
30. 作为项目维护者，我希望公开请求按连接对端识别且忽略伪造转发头，以便客户端不能自行切换限流身份。
31. 作为项目使用者，我希望容器地址和端口发布清楚，以便能够访问演示而不意外开放数据库和 broker 业务端口。
32. 作为项目维护者，我希望数据库和 RabbitMQ 使用项目账号，以便应用不依赖默认 root 或 guest 凭据。
33. 作为项目维护者，我希望管理令牌和访客 HMAC 独立生成且不提交仓库，以便示例不会成为实际秘密。
34. 作为项目维护者，我希望身份密钥跨普通重启稳定，以便 UV 身份不会每次重启都被拆分。
35. 作为项目维护者，我希望基础配置采集默认关闭、完整演示显式开启，以便运行模式和文档一致。
36. 作为项目维护者，我希望 MQ 不健康不阻止核心启动和跳转，以便统计继续保持 best-effort 隔离边界。
37. 作为运维查看者，我希望区分应用存活、核心就绪和依赖/统计状态，以便不因 MQ 故障误判整个应用死亡。
38. 作为运维查看者，我希望通过最小指标观察限流、回源、缓存和 MQ 结果，以便知道拒绝或漏记发生在哪个边界。
39. 作为运维查看者，我希望指标使用固定低基数标签，以便 IP、短码和任意路径不会造成指标数量膨胀。
40. 作为运维查看者，我希望日志保留请求定位和安全错误类别，以便能够排查协调未确认和依赖降级。
41. 作为匿名访客，我希望原始身份、IP和完整访问元数据不进入普通日志，以便运行观测不会扩大隐私数据保存范围。
42. 作为项目维护者，我希望高频拒绝不会逐条刷日志，以便防刷功能本身不制造资源消耗。

52. 作为项目维护者，我希望本阶段有明确停止线，以便完成工程化后不再为了技术名词继续增加组件。

### 架构与职责

1. 保留单模块 Java 17 / Spring Boot 应用，以及单节点 MySQL、Redis、RabbitMQ。统计发布和消费继续在同一个应用进程，不拆新服务，不改变既有业务表和消息协议。
2. 增加一个内聚的限流判定模块，向 HTTP 层表达获准、额度不足、依赖不可用及必要等待提示；Redis/Lua/时间/TTL封装在其实现中。业务服务不接触管理令牌或 HTTP 响应。不为本阶段增加通用仓储、多个透传包装或一套泛化限流框架。
3. HTTP 层识别固定请求组并执行鉴权/格式校验/限流顺序；跳转用例在实际数据库加载边界执行并发准入。缓存命中、共享等待、统计采集和错误映射仍由现有职责承接。

### 接口、身份与算法

4. 只实现 Redis + Lua 令牌桶；不同组使用同一算法、独立参数与状态。固定窗口和滑动窗口属于说明与面试比较，不实现多套算法。

| 请求组 | 身份 | 桶容量 | 补充速率 | 限流依赖失败 |
| --- | --- | --- | --- | --- |
| POST /api/links | 连接对端 IP + 创建组 | 3 | 每 6 秒 1 个 | 业务前 fail-close |
| GET/HEAD /s/{code} | 连接对端 IP + 跳转组，跨短码共享 | 60 | 每秒 10 个 | fail-open |
| PUT /api/links/{code}/enabled | 鉴权后固定共享管理写组 | 5 | 每秒 1 个 | 业务前 fail-close |
| GET/HEAD /api/internal/links/{code}/stats、/visits | 鉴权后固定共享管理查询组，两接口共用 | 5 | 每秒 1 个 | 查询前 fail-close |

5. 所有额度参数可配置并启动校验。桶初始化满，获准消耗一个令牌，补充不超过容量；不能将其宣传为严格的任意滚动窗口次数上限。静态资源和健康探针不消耗业务额度，不新增专门未授权请求限流层。
没有用户模型，不把 UV Cookie 当可靠防刷身份，不使用逐短码桶或原始管理令牌 Key。
7. 创建在请求体解析及发号/写库前限流。跳转先做廉价格式校验，非法格式保持 404 且不访问 Redis/MySQL；合法格式再限流，再读取缓存或数据库。管理先执行原鉴权，再限流，再解析参数与执行业务；未配置404、缺失/错误/重复头401保持，鉴权拒绝不访问限流 Redis 或 MySQL。
8. 获准请求后续400/404/403/410/500/503不退还令牌；额度不足不扣成负数。原有创建无请求幂等键、同一原始 URL 可产生多个映射的契约保持。

### Redis原子性、状态与错误

9. 限流复用单节点 Redis，但命名空间与跳转版本缓存隔离。Lua 在一次短且有界的执行内完成读取、补充、判断、扣减和 TTL 更新，防止最后令牌并发重复获准；不扫描 Key，不动态产生无限脚本，不加入分布式锁。
10. 以 Redis TIME 计算补充，状态闲置 TTL 不短于空桶补满时间；验证数值、时钟异常和溢出边界，不允许负令牌或超过容量。TTL 是闲置清理，不是全局内存上限。
11. 使用参数化脚本及 EVALSHA/NOSCRIPT 安全重载；扣减网络超时可能已执行，不盲目重试，按组故障策略处理。核对客户端离线排队/重连行为，不增加不确定扣减的无限重试。Lua 不提供自动回滚、MySQL联合事务或永久配额。
12. 明确额度不足返回429 RATE_LIMIT_EXCEEDED、Retry-After向上取整到秒及Cache-Control: no-store；等待提示不承诺下次必获准。HEAD无响应体。限流无法确认的创建/管理请求返回业务开始前的独立503，不发号、不写库、不查询、不误报已创建。
13. 回源繁忙503、限流不可用503与既有 CREATE_CACHE_COORDINATION_UNCONFIRMED、LINK_STATE_CACHE_COORDINATION_UNCONFIRMED 使用不同错误码。后两者继续表示 MySQL 已提交、协调未确认。实现时固定新增错误码并同步页面、文档和验收，页面不能把所有503都解释为已保存。
14. 限流和回源保护拒绝不设置统计Cookie、不生成访问事件、不计PV/UV。正常GET作出跳转决定后继续最小化采集和best-effort异步交接；HEAD不计数。Redis限流故障放行后最终正常GET仍可采集，不把放行误当拒绝。

### 回源保护与资源

15. 实际跳转数据库加载每实例同时最多4个、可配置，正常miss、Redis故障回源及等待共享任务超时后的实际独立查询均适用。缓存命中/共享任务等待者不占许可，一次共享实际加载只占一次；真实查询完成或失败后释放，不能因等待者超时提前释放仍在执行的查询。
16. 无许可立即独立503，不增加等待队列，不写为负缓存或访问事件。Redis限流fail-open仅允许进入跳转流程，仍受回源保护。此上限不是独占连接预留、全部数据库工作负载或集群总上限。

| 资源 | 可配置起点 |
| --- | --- |
| 核心数据库池 | 最大8；连接获取等待500ms |
| 统计数据库池 | 保留最大4及写/查询/清理准入2/1/1 |
| 跳转实际回源 | 每实例4 |

17. Redis内存满时相关操作按失败及既定降级处理，不主动淘汰限流桶静默重置额度。演示不持久化Redis，重建/清理后的额度重置可接受，但缓存仍遵守既有受控恢复规则。保持现有Redis连接/命令200ms短超时，不增加自动熔断或故障冷却；单次预算不保证HTTP总截止。
18. 资源数字是待实测修正的演示起点，不是最低机器要求或总进程内存保证；堆外内存、引擎、构建与测试设施需要余量。

20. 仅向localhost发布应用、Actuator管理及RabbitMQ Management端口，MySQL/Redis/AMQP默认不向宿主发布；调试使用独立override/profile。
21. 第一次初始化生成被Git忽略的独立管理令牌/HMAC和DB/MQ凭据，数据库和broker使用项目账号/vhost，仓库仅留占位示例。身份密钥普通重启不变化，秘密轮换与数据重置分别说明，不在输出/日志中打印秘密。
22. 数据库与MQ policy初始化可复现、有明确来源，重复执行不删数据、队列或积压。已有卷中的账号状态不一定随环境变量自动改变，需要准确说明。应用核心启动只等待MySQL健康，不把Redis/MQ健康设为核心硬依赖；完整演示必须验证全部组件、路由、policy和消费者。healthcheck不提供高可用或运行期自动恢复承诺。

### 可观测性、文档与展示

23. Actuator分组：liveness仅自身；core readiness包含应用就绪与核心MySQL，不能错误聚合统计池；Redis/MQ/统计采集消费意图及实际状态另列。Redis故障时核心就绪不承诺创建/管理可用。探针不能启停消费者或改写人工暂停意图。
24. 管理端口仅开放health/info/metrics，主端口仅无详情存活/就绪探针；禁用env/configprops/heapdump/动态日志修改。info只提供安全构建信息，健康不泄露连接/SQL/秘密/原始异常。
25. 统一必要的HTTP次数/耗时、限流结果、回源在途/拒绝、缓存结果/失败、池状态以及现有MQ终局和统计丢弃观察。broker ready/unacked继续由受限Management/观察入口核验。标签只使用模板路由、请求组与固定结果类别，不使用IP、短码、URL、访客标识、eventId/requestId或任意请求路径。
