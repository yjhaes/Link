# 01：消费者幂等异常验证与验收

## Parent

[阶段 7：消费者幂等边界与异常验证](../spec.md)

## What to build

补足同一访问事件不重复入账的两类异常证据：真实 MySQL 的并发首次插入，以及真实提交后数据库确认丢失、消费者原事件重试判重、最终 ACK 与统计查询的完整链路。内部管理者可以通过日志、PV、UV 和访问明细验证只有一次入账；维护者可以通过消费终局和队列状态确认消息已经安全处理。

用户已确认将原拟两张独立任务合并为本任务。任务包含两类测试、相关回归和实际验收记录，无外部任务阻塞，不需要前置重构。

保留当前 eventId、MySQL 事件唯一索引、同步 listener 与 AUTO 确认、每轮有限重试、DLQ、日志统计及三十日窗口。只有测试暴露实际问题时才作最小修复，不要求为了验收新增生产功能。

## Acceptance criteria

### 同事件并发首次入库

- [x] 使用真实 MySQL，通过既有持久化确认入口，让两个并发调用处理同一个尚未保存的 eventId，事件字段相同且位于有效统计窗口。
- [x] 真实覆盖首次插入竞争，不以预先已有日志、准入拒绝或锁超时替代成功竞争；断言一个 SAVED、一个 DUPLICATE，最终仅一条该事件日志。
- [x] 不调整生产写入容量或唯一键机制来迁就测试，不将应用先查后写作为幂等保障。

### 提交未知到 ACK 和统计的完整链路

- [x] 使用隔离的真实 RabbitMQ 与 MySQL，通过现有消息协议、listener 及持久化链路处理一个合法事件。
- [x] 首次 INSERT 真实提交后，由测试侧故障注入模拟成功响应丢失，使持久化向消费者暴露 UNCERTAIN；执行前抛异常或纯 mock 不替代真实提交未知。
- [x] 后续尝试保留原 eventId、发生时间、统计日和访客数据，得到 DUPLICATE，消费取得明确终局后正常返回并由容器 ACK。
- [x] 消费终局为 DUPLICATE，不把数据库首次实际保存误断言为消费者首次已经取得 SAVED 确认；注入仅影响指定事件的首次结果，后续资源可正常使用。
- [x] 最终仅一条该事件日志；经既有统计和明细查询 API 验证 PV=1、UV=1、明细一条，使用隔离映射、固定访客及有效日期范围。
- [x] 停止新输入后，使用有界最终等待确认业务队列 ready/unacked 均归零，DLQ 无意外消息；不能只凭日志出现就宣称 ACK 已完成。

## Further notes

- 事件身份用于区分访问事件，匿名访客身份用于 UV，两者不能混用。独立新 GET 产生新 eventId，同事件重试、重投、重放保持原身份及冻结数据。
- 当前是每轮最多三次，不是消息整个生命周期最多执行三次；结果未知或进入 DLQ 不表示数据库未执行。
- 同一事件在有效统计窗口内由唯一键避免重复记录，超窗合法事件不再入库。继续保持 best-effort，不承诺端到端不丢或严格 Exactly Once。
- 本任务的发布不表示已开始实施，不自动进入阶段 8。
