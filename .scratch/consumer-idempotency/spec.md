Status: resolved

## Problem Statement

当前 RabbitMQ 异步访问统计已经完成，项目已有访问事件身份、MySQL 事件唯一索引、同步消费与 AUTO 确认、有限分类重试、DLQ 和保留窗口检查。内部管理者需要确信同一访问事件被重复处理时不会重复生成日志或增加 PV；项目维护者也需要准确解释数据库结果未知、提交至 ACK 间隙、重投及日志清理后的保障边界。

现有测试已经覆盖真实提交后消费连接断开及恢复判重、持久化响应丢失后的同 ID 判重、分类重试、窗口规则和独立访问的身份。剩余验证缺口集中在两个场景：同一个新 eventId 的并发首次插入，以及真实提交后结果未知、消费者重试判重、最终 ACK 与统计查询结果贯通的完整链路。

本阶段目标是保留合理的既有方案，补足上述证据并整理可解释的幂等契约，不把已完成的能力重新实现。项目继续用于访问流量观察，允许故障漏记，不升级为可靠计费账本或端到端 Exactly Once 系统。

## Solution

继续让每个独立访问事件具有新 UUID，同一事件的重试、重投和重放保留原 eventId 及冻结数据。消费者直接向 MySQL 访问日志插入，唯一键阻止同一事件重复记录；只将事件唯一键冲突视为合法重复。PV、UV 和明细共用访问日志这一权威数据源。

执行结果未知时沿用原事件有限重试，明确保存或判重后正常返回并由容器确认；合法超窗事件确认丢弃，永久错误或重试耗尽拒绝且不 requeue。保留每轮最多三次与窗口检查，不维护跨重启累计次数或独立长期去重表。

使用既有持久化入口、真实消息消费路径及统计查询 API 补两类异常测试。只有验证发现实际问题时才作最小修复；没有问题则保留生产实现。完成后记录实际运行的验证范围和结果，清楚区分既有证据、新增通过证据与保障之外的能力。

## User Stories

以下描述需要保留的业务契约与新增验收目标，不表示所有能力都尚未实现。

1. 作为短链接访问者，我希望统计故障仍不阻断正常跳转，以便非核心业务不会降低主要服务可用性。
2. 作为内部管理者，我希望每个独立正常 GET 访问产生独立事件身份，以便真实访问不会被消息防重合并。
3. 作为内部管理者，我希望刷新和客户端重新发起 GET 分别计入 PV，以便统计保持既有请求口径。
4. 作为内部管理者，我希望同一访问事件的重复处理沿用原身份，以便访问日志不会重复增加。
5. 作为内部管理者，我希望同一事件的处理重试保持原发生时间和统计日，以便消息延迟不会改变历史归属。
6. 作为内部管理者，我希望重放保留访客摘要与密钥版本，以便重复处理不会改变 UV 归属。
7. 作为项目维护者，我希望数据库唯一索引处理同事件的写入竞争，以便多次执行仍最多产生一条已提交日志。
8. 作为项目维护者，我希望并发首次插入有真实 MySQL 测试证据，以便唯一约束的保障不只是顺序重试结论。
9. 作为项目维护者，我希望仅事件唯一键冲突被视为已处理，以便其他约束错误不会被误 ACK。
10. 作为项目维护者，我希望执行超时或断连被识别为可能结果未知，以便不会错误断言数据库尚未执行。
11. 作为项目维护者，我希望结果未知后使用原 ID 重试，以便首次已提交时可以安全判重。
12. 作为项目维护者，我希望完整消费链路覆盖真实提交后响应丢失，以便持久化与消费者之间的故障处理得到联合验证。
13. 作为项目维护者，我希望确认保存后资源关闭失败仍保留成功结果，以便明确结果不会被清理错误改成未知。
14. 作为内部管理者，我希望数据库提交后 ACK 丢失造成重投时仍只有一条日志，以便 PV 不重复增加。
15. 作为项目维护者，我希望 listener 在同步业务处理得到终局后才正常返回，以便 AUTO 不提前确认消息。
16. 作为项目维护者，我希望合法重复正常确认，以便已完成事件不会反复进入失败处理。
17. 作为项目维护者，我希望合法超窗事件确认丢弃，以便历史消息不会重新插入已清理日志。
18. 作为项目维护者，我希望暂时错误、繁忙或提交未知每轮最多尝试三次，以便故障不会形成单轮无限处理。
19. 作为项目维护者，我希望永久错误不重试、耗尽后拒绝且不 requeue，以便毒消息与持续故障有明确终局。
20. 作为项目维护者，我希望区分每轮尝试上限与跨断线重投，以便不会宣称消息整个生命周期最多执行三次。
21. 作为项目维护者，我希望不使用 redelivered 标记决定是否执行唯一键检查，以便重新发布的同事件仍有防重保障。
22. 作为项目维护者，我希望不因 redelivered=true 就跳过处理，以便尚未入库的事件仍有保存机会。
23. 作为项目维护者，我希望知道 DLQ 中的消息可能已经入库，以便排查和重放不会误生成新 ID。
24. 作为项目维护者，我希望数据库持续故障时沿用观测与人工暂停，以便不把有限重试误解为自动止损。
25. 作为内部管理者，我希望 PV 使用已记录事件数量，以便消费尝试数或 broker 确认数不会被误当访问次数。
26. 作为内部管理者，我希望 UV 按匿名访客摘要及密钥版本去重，以便同访客的新访问增加 PV 而不重复增加范围 UV。
27. 作为内部管理者，我希望范围 UV 对整个范围去重，以便跨日访客不会因累加日 UV 而重复计数。
28. 作为内部管理者，我希望访问明细与 PV、UV 来自同一份日志，以便异常测试可以同时验证统计与记录。
29. 作为内部管理者，我希望保留最近三十个上海统计日的查询口径，以便窗口不被误解为从入库开始计算的固定时长。
30. 作为项目维护者，我希望每次重试前重新检查统计窗口，以便跨午夜的旧事件不会绕过保留规则。

## Implementation Decisions

- 保留既有访问采集、消息协议、消费、持久化、统计查询和清理模块的职责及公开接口；本阶段主要新增异常验证，没有预设生产代码改造。
- 访问采集在逐请求边界调用 UUID.randomUUID() 生成 eventId；新访问与消费尝试是不同概念，同事件始终保持身份及冻结字段不变。
- 保留 MySQL 访问日志的 BINARY(16) event_id 与 uq_visit_event 唯一索引。直接 INSERT，不先查后写，不新增表、索引或迁移。
- 持久化确认保留 SAVED 与 DUPLICATE；仅明确的事件唯一键冲突返回 DUPLICATE。保留 BUSY、TRANSIENT、PERMANENT、UNCERTAIN 分类，其他约束错误不得转为重复成功。
- 执行阶段响应丢失不能证明未提交；沿用原事件重试，不换 ID，也不另行先查数据库判断是否重试。已明确保存后的资源关闭失败保持 SAVED。
- 保留同步 listener、Spring AUTO 与 batchSize=1。成功保存、事件重复或合法超窗丢弃可以正常返回；持久化失败不得静默返回，不转交异步落库任务后提前确认。
- 保留每轮最多三次，包括首次，重试等待 200ms、500ms。暂时错误、繁忙、提交未知可重试，永久错误不重试；耗尽后拒绝且不 requeue，沿用既有死信路由。
- 断线或崩溃可能使未确认消息开启新一轮消费。上限不覆盖消息整个生命周期；不新增持久尝试计数，也不以 redelivered 或 channel delivery tag 代替事件身份。
- 保留单一 DLQ 排查与人工暂停流程，不自动回流。进入 DLQ 不表示数据库没有保存，重放仍用原事件身份和时间。
- MySQL 日志仍为统计权威。PV 为范围内行数，UV 为整个范围内访客摘要与密钥版本的去重数，明细来自同一张日志；不维护单独的计数器或汇总表。
- 现有自动提交模式的单条 InnoDB INSERT 本身具有事务边界，当前不加额外显式写事务。保留现有只读一致性查询事务；若将来加入汇总写入，再另行设计日志防重与汇总更新的同库事务。
- 保留包含当天的最近三十个上海自然日，每次持久化尝试前按原统计日检查窗口。合法超窗事件不写库而确认丢弃，未来日或日期不一致拒绝；人工重放不修改冻结时间。
- 窗口检查后执行跨午夜可能暂时留下超窗物理行，由既有清理追赶，查询仍严格限制窗口。不新增长期去重表或历史补采能力。
- 不增加 Redis 幂等层。先标记再入库可能漏记，先入库再标记仍需数据库判重；现有业务写入与唯一检查已由同一数据库操作完成。
- 后续验证如暴露实际问题，只作满足上述契约的最小修复，并补相应回归，不扩大成新的可靠性架构。

### 测试边界与确认依据

用户已在 Q9 选择 B，确认使用真实 MySQL 验证并发首次插入，并补真实提交后结果未知到重试、判重、最终 ACK 的完整链路；Q10 再次确认完整共识。本规格沿用这两个已确认边界。

优先选择现有最高可用边界：并发场景通过既有持久化确认入口与真实数据库验证；完整链路通过真实 broker 投递、现有 listener、真实日志写入和既有统计／明细查询 API 验证。不新增业务端点、生产测试模式或为测试暴露私有实现。

好测试应断言外部结果：持久化确认、日志数量、队列终局及 API 返回的 PV、UV、明细。闩锁或 JDBC 代理仅用于精准制造故障，不能以测试私有方法、SQL 文本或调用顺序代替最终业务结果。使用隔离短码、固定访客身份、受控日期、独立测试依赖和有界最终等待，避免无界等待与长时间固定 sleep。

### 新增验收一：同 ID 并发首次插入

- 使用真实 MySQL 与现有持久化模块，让两个调用在同一并发场景处理同一个尚未保存的 eventId，事件字段完全一致，统计日在有效窗口内。
- 保证场景不被数据库故障、准入拒绝或预先保存的日志替代，真正覆盖首次成功插入竞争。
- 断言一个结果为 SAVED、另一个为 DUPLICATE，最终只有一条该事件日志。
- 不修改并发容量或生产唯一键机制来配合测试；可复用现有测试上下文及同步工具。
- 已有同 ID 的锁超时／准入释放测试不能冒充本场景的成功竞争证据。

### 新增验收二：真实提交后结果未知的完整链路

- 使用隔离的真实 RabbitMQ 与 MySQL，经现有消息协议投递一个合法事件。
- 首次 INSERT 在数据库真实提交后，通过测试侧故障注入模拟成功响应丢失，使持久化对消费者暴露 UNCERTAIN；不能在执行 SQL 前抛异常来替代提交未知。
- 下一次持久化尝试仍使用原 eventId 和冻结字段，返回 DUPLICATE，消费取得明确终局并正常确认。
- 断言该事件只有一条日志，既有查询 API 返回 PV=1、UV=1，明细恰好一条；查询需使用隔离映射、固定身份及与事件对应的有效日期范围。
- 在停止新输入后，以有界最终等待确认业务队列 ready/unacked 均归零且 DLQ 没有意外消息，避免仅凭日志出现就宣称 ACK 完成。
- 消费终局应为 DUPLICATE；数据库首次实际保存不等于消费者首次已取得 SAVED 确认，不强制错误的成功分类计数。
- 故障注入只影响指定事件和首次确认，后续重试能使用正常资源；测试结束清理线程、连接与隔离消息，避免影响其他用例。

## Out of Scope

- 新增 eventId、事件唯一索引、有限重试、DLQ 或 AUTO ACK 的重复建设；这些能力已经存在。
- Redis SETNX 幂等状态、分布式锁、永久事件去重表、汇总表、Redis 统计计数或多存储双写。
- 改为 MANUAL ACK、提前 ACK、异步落库后正常返回、无限 requeue、自动 DLQ 回流或长期补偿工具。
- 分布式事务、MQ 事务、outbox、端到端不丢或严格 Exactly Once、跨重启累计尝试上限。
- 窗口外历史补采、通过修改 eventId 或时间重新入账、重放同 ID 不同业务载荷的处理协议。
- 新增消息队列、微服务、集群、批量处理、吞吐优化或性能基准；没有证据需要这些改动。
- 改变匿名访客身份、统计口径、隐私最小化、管理鉴权、核心跳转、缓存协议或阶段 8 功能。
