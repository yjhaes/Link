Status: ready-for-agent

## Problem Statement

内部管理者需要按短码启用或禁用一条短链接映射。目前系统只有创建和跳转 HTTP 接口，启用状态虽然已经保存在数据库中，但维护者仍需直接修改数据库并调用内部缓存协调方法才能确认操作完成。

直接修改数据库无法完整表达过期限制、重复操作、并发写入和部分完成结果。系统还缓存可跳转、已禁用等结果，如果数据库更新后缓存没有同步，访问者可能继续收到旧结果。维护者需要一个能够清楚说明成功、拒绝和数据库已更新但缓存同步未确认的统一接口，并在短暂缓存故障时自动尝试恢复。

## Solution

增加一个内部管理 HTTP 接口，按短码显式设置目标启用状态，不采用自动翻转状态的操作。本次只增加后端接口，沿用当前内部管理的使用范围，不增加页面操作或账号体系。

接口拒绝对已过期的短链接映射执行任何状态操作，也拒绝重复启用或重复禁用。成功时返回短码和本次提交的启用状态。同一码的并发操作按照数据库提交顺序生效。

数据库只更新一次，提交后沿用现有缓存版本轮换与结果清除协议。缓存同步在当前请求内最多尝试三次，两次重试前分别等待 50 毫秒和 100 毫秒。确认同步成功才返回成功；三次均未确认成功则返回 503，明确数据库已更新、缓存同步未确认，并附带短码。请求结束后不继续自动重试。

## User Stories

1. 作为内部管理者，我希望按短码禁用一条未过期的短链接映射，以便主动停止该短链接的跳转。
2. 作为内部管理者，我希望按短码重新启用一条未过期的已禁用映射，以便恢复原短链接的使用。
3. 作为内部管理者，我希望通过一个接口显式提交目标启用状态，以便准确表达操作意图。
4. 作为内部管理者，我希望重新启用时保留原短码和原始 URL，以便已有短链接能够继续使用。
5. 作为内部管理者，我希望状态操作不修改原始有效期，以便启用不会延长有效时长。
6. 作为内部管理者，我希望已过期映射不能启用，以便过期短链接不会通过状态维护重新获得跳转能力。
7. 作为内部管理者，我希望已过期映射也不能禁用，以便过期后的所有新状态操作使用一致的拒绝规则。
8. 作为内部管理者，我希望重复启用返回明确的冲突错误，以便发现不符合当前状态的操作。
9. 作为内部管理者，我希望重复禁用返回明确的冲突错误，以便区分操作已经完成与新的状态变更。
10. 作为内部管理者，我希望已过期且状态重复时优先得到过期错误，以便准确理解操作被拒绝的主要原因。
11. 作为内部管理者，我希望不存在的短码返回找不到映射的错误，以便避免把不存在误认为已禁用。
12. 作为内部管理者，我希望非法短码和无效请求体被明确拒绝，以便错误输入不会修改映射。
13. 作为内部管理者，我希望成功响应包含短码和启用状态，以便识别本次提交的结果。
14. 作为内部管理者，我希望并发操作按照数据库提交顺序生效，以便最终状态有明确的判定依据。
15. 作为内部管理者，我希望并发重复操作仍受到重复状态检查，以便多个请求不会都把同一次状态变化报告为成功。
16. 作为短链接访问者，我希望禁用操作成功后才开始的访问收到已禁用结果，以便禁用能够及时生效。
17. 作为短链接访问者，我希望重新启用成功后才开始的访问不再被旧禁用缓存拒绝，以便恢复使用无需等待缓存自然到期。
18. 作为短链接访问者，我希望过期仍优先于禁用，以便访问结果准确反映业务有效期。
19. 作为短链接访问者，我希望合法跳转仍返回原始 URL，以便新增管理接口不改变正常跳转行为。
20. 作为内部管理者，我希望短暂的缓存同步失败在当前请求内自动重试，以便减少手工恢复的需要。
21. 作为内部管理者，我希望自动重试有明确次数和等待间隔，以便请求不会无限等待恢复。
22. 作为内部管理者，我希望缓存同步重试不再次修改数据库状态，以便旧操作不会覆盖后来提交的反向操作。
23. 作为内部管理者，我希望缓存同步已执行但响应丢失时仍可以安全重试，以便处理结果不确定的超时。
24. 作为内部管理者，我希望三次同步均失败时得到带短码的 503，以便定位尚未确认完成的操作。
25. 作为内部管理者，我希望 503 明确说明数据库已更新，以便不会误以为操作已回滚并盲目重放状态请求。
26. 作为内部管理者，我希望业务拒绝和数据库失败不触发缓存同步重试，以便不会把非缓存错误当作可恢复的同步故障。
27. 作为内部管理者，我希望未确认同步的日志能够按短码定位，以便后续使用既有内部恢复方法处理。
28. 作为项目实现者，我希望复用已有 HTTP、服务和真实数据库/缓存测试边界，以便用可重复的测试验证行为而不新增复杂测试设施。

### API 契约

- 新增 PUT /api/links/{code}/enabled。code 为原有短码，保持大小写敏感和现有 4 至 8 位 Base62 格式规则。
- 请求体包含必填布尔字段 enabled，true 表示启用，false 表示禁用。缺失、null、非布尔输入及不可解析的请求体使用现有 400 INVALID_REQUEST 语义；不将缺失值默认为禁用。
- 格式非法的短码沿用 404 LINK_NOT_FOUND，且不访问数据库或 Redis。格式合法但映射不存在时也返回 404 LINK_NOT_FOUND。
- 成功返回 200，响应包含 shortCode 字符串和 enabled 布尔值。enabled 表示本次已提交操作的目标状态，不承诺响应到达时没有发生后续操作。
- 对已存在映射先判断是否过期，再判断目标状态是否重复。到期当刻及以后，不论目标状态如何，均返回 410 LINK_EXPIRED。
- 未过期映射已启用且目标为启用时返回 409 LINK_ALREADY_ENABLED；已禁用且目标为禁用时返回 409 LINK_ALREADY_DISABLED。
- 数据库状态更新已确认提交、但三次缓存同步均未确认成功时返回 503。响应采用现有错误模型的 code、message 并附带 shortCode；code 必须能区分状态变更的同步未确认与创建的同步未确认，具体名称沿用实现时的命名规范。message 明确说明数据库状态更新已提交、缓存同步未确认，不能声称数据库已经回滚。
- 状态成功响应和错误响应均不允许 HTTP 缓存，沿用现有 no-store 约定。
- 重复状态请求的响应并不幂等成功：数据库状态不会因重复请求再次变化，但接口按已确认要求返回 409。

### 模块职责与持久化

- 扩展现有控制器和错误响应映射，增加专门的状态维护应用用例，不把状态更新放进创建或跳转职责。
- 复用现有映射的 enabled、expiresAt 与短码主键。无需增加字段、表、业务版本参数或发号步骤。
- 状态维护以 MySQL 为权威数据源，不能凭跳转缓存中的结果判断是否允许修改。
- 扩展现有持久化边界，使映射存在性、过期和重复状态的判断与更新针对同一受保护的当前状态完成。不能先读取旧状态，再在没有并发保护的情况下无条件覆盖。
- 同一码的状态操作通过数据库提供的原子性和并发控制按提交顺序生效，不依赖仅覆盖单个进程的锁。相同目标的并发请求在前一个变化已提交后应按当前状态拒绝重复操作；只有通过业务校验并提交的操作参与最终状态判定。
- 使用现有 UTC 时间和数据库时间精度规则，在状态判定/更新时检查当前有效期。等待并发操作后需要依据当前状态和当前时间重新判断，不能沿用等待前的快照。
- 更新只改变 enabled，保留短码、原始 URL、创建时间和过期时间。业务拒绝不写入数据库，不执行缓存协调。
- 应用用例必须确认状态更新已提交，再进入缓存同步阶段；不得在尚未提交的外层事务中报告操作成功。数据库更新失败或提交未确认沿用现有服务错误语义，不报告“数据库已更新”的 503，不执行缓存同步重试。

### 缓存一致性与有限重试

- 遵守 ADR-0004 的版本轮换、结果清除及带版本条件回填协议；不能退回仅删除缓存、等待 TTL 或协调失败仍返回成功的旧方案。
- 数据库提交后复用 RedirectCache 的 replaceVersion 能力，用全新版本占位替换业务缓存结果。所有缓存结果的条件回填和按短码加版本的实例内请求合并继续遵守已有协议。
- 缓存同步总共最多三次，包括第一次尝试和两次重试。第一次立即执行；第一次失败后等待 50 毫秒，第二次失败后等待 100 毫秒；第一次或第二次确认成功时立即停止，第三次失败后不再等待或尝试。
- 每次重试只轮换缓存版本并清除业务结果，不重新执行状态校验或数据库更新，不把旧请求的 enabled 写入缓存，不重新发号或插入映射。
- 数据库状态只更新一次。即使较早操作的缓存重试晚于较新的反向操作，其同步也只能使下一次读取回源当前数据库状态，不能恢复旧业务状态。
- 同步超时表示结果未确认，不代表 Redis 一定没有执行。重复版本轮换必须保持安全，包括命令已生效但响应丢失的场景。
- 只有状态提交和缓存同步均确认后才返回 200。成功之后新开始的访问应按更新后的状态判断，受后续合法操作与自然过期影响；与变更重叠的旧访问允许按原快照完成。
- 过期检查约束新的状态操作。合法状态操作已提交后，即使在重试期间自然过期，也继续完成缓存同步，不回滚或重新解释已提交的业务操作；后续跳转仍按过期判断返回 410。
- 三次尝试均失败时记录能按短码定位的未确认同步日志并返回 503。请求返回后停止重试，不启动后台任务，不保存持久补偿记录。
- 保留现有内部协调恢复能力作为耗尽后的恢复手段，仅恢复缓存同步；重复 PUT 状态请求不能被当作协调恢复请求，它仍按当前状态执行业务校验。
- Redis 连接和命令的现有 200 毫秒超时继续沿用。两次等待累计 150 毫秒，但这不是整个 HTTP 请求的最大耗时保证。
- 此次自动重试范围仅为新增状态维护用例，不顺带改变已有创建接口的重试策略。

### 领域与现有架构关系

- “已禁用”与“已过期”仍是独立领域状态。新增 API 不允许过期后的状态维护，不意味着合并这两个概念，也不改变现有跳转拒绝结果的分类。
- 既有跳转语义保持：可跳转为 302，不存在为 404，已过期为 410，未过期且已禁用为 403，并保留 Location 与 no-store。
- 本规格增补 ADR-0004 当时不增加维护 HTTP API 的范围，保留其全部缓存协调与故障边界要求。原有直接 SQL 与内部恢复示例描述的是历史维护入口，不能用于证明新 HTTP API 允许过期操作。
- 多实例仍共享同一 MySQL 主写库和同一 Redis 主实例。即时可见保证不扩展到已确认写入丢失、旧快照恢复或自动故障切换；继续遵守既有受控恢复流程。

### 测试边界与既有先例

- 以现有 HTTP 接口验收边界为主，通过状态维护请求、响应与随后发起的跳转请求验证外部行为，并核对数据库中映射的最终状态。
- 复用 ShortLinkApiTest 的 MockMvc、真实 MySQL、可控时钟和测试缓存边界，覆盖请求契约、拒绝结果、状态更新和过期判断。
- 复用 RedisRedirectIntegrationTest 的真实 MySQL/Redis、独立应用上下文和受控并发同步点，验证版本协议、提交顺序、旧缓存回填及跨实例可见性。
- 复用 ShortLinkUseCasesTest 的服务输入/输出边界和可控依赖，验证暂时失败、重试耗尽、数据库失败与后续反向操作安全性。仅在现有边界无法控制等待时，为重试等待提供最小可控依赖，不暴露新的生产 HTTP 测试入口。
- 测试以公开行为和持久化结果为依据。不得仅凭调用私有方法、响应相同或 Redis 最终值正确宣称并发一致性成立。重试次数和间隔属于已确认行为，可以通过可控缓存故障与等待记录验证。
- 用户已确认以上测试边界；本次仅记录测试计划，不声称已经新增或运行这些测试。实现时不要求增加新的测试框架。

### 验收场景

| 场景 | 应验证的外部结果 |
| --- | --- |
| 禁用未过期映射 | 返回 200 和本次 shortCode、enabled=false；数据库仅状态变化，随后新跳转返回 403 LINK_DISABLED。 |
| 重新启用未过期映射 | 返回 200 和 enabled=true；原短码、原始 URL、过期时间保持，随后新跳转返回 302。 |
| 永久映射 | 可以启用和禁用，不引入过期时间。 |
| 重复启用/禁用 | 分别返回 409 和对应错误码；没有数据库状态变化或缓存协调。 |
| 已过期映射 | 启用、禁用、重复目标均返回 410，不改变 enabled；覆盖到期当刻及之后。 |
| 过期优先 | 已过期且已禁用时请求禁用仍返回 410，不能先返回重复状态 409。 |
| 非法和不存在短码 | 按现有格式及大小写规则返回 404；非法格式不访问持久化或缓存边界，合法不存在不执行更新或协调。 |
| 无效请求体 | enabled 缺失、null、非布尔值、畸形 JSON 返回 400 INVALID_REQUEST，不改变状态。 |
| 一次成功 | 同步首次确认成功即返回 200，没有额外重试或等待。 |
| 暂时同步失败 | 第一次失败、第二次成功，或前两次失败、第三次成功，最终返回 200；数据库均只更新一次。 |
| 重试次数和间隔 | 三次均失败时总计三次尝试，重试前依次等待 50、100 毫秒；耗尽后不再等待或自动尝试。 |
| 部分完成 | 返回 503 及短码，message 明确数据库已更新、同步未确认；数据库保留已提交状态。 |
| 503 后重复请求 | 再次提交同一目标按当前数据库状态返回 409，不把重复业务请求当作同步恢复。 |
| 数据库失败 | 提交未确认不进入缓存同步，不返回“数据库已更新”的 503，不尝试重新更新。 |
| 同步已执行但响应丢失 | 安全重试并最终成功，或耗尽返回未确认；不重复数据库更新，不恢复旧状态。 |
| 重试期间过期 | 已提交操作继续完成同步；随后跳转返回 410，重试不修改有效期。 |
| 并发同目标 | 用受控顺序证明前一个有效变更提交后，另一个请求按当前状态返回 409；不是两次都成功。 |
| 并发反向操作 | 使用可控交叠按实际数据库提交顺序核对最终状态；旧操作的延迟同步不能覆盖新状态。 |
| 等待期间到期 | 等待其他状态操作后以当前时间判断，已经到期则返回 410，不使用等待前的有效快照。 |
| 禁用后的迟到旧正值 | 暂停旧查询，禁用并确认完成后恢复旧回填；完成后新跳转仍为 403。 |
| 启用后的迟到旧拒绝结果 | 暂停旧已禁用查询，启用并确认完成后恢复旧回填；完成后新跳转为 302。 |
| 独立实例 | 一个实例完成维护后，另一独立实例开始的访问按当前状态响应，不加入旧版本加载任务。 |
| 回归与 HTTP 缓存 | 创建和原有四类跳转结果不变，状态成功与错误响应均带 no-store。 |

- 并发测试用闩锁或等效同步点控制顺序，时间边界用可控时钟，不通过长时间 sleep 或偶然线程调度证明正确性。
- 可控故障验证完整重试序列，少量真实 Redis 超时或断连验证适配器行为；故障注入仅用于隔离测试环境。
- 不编写重复验证框架内部实现的测试，也不为本次未实现的后台补偿或页面操作编写测试。

## Out of Scope

- 页面上的启用/禁用按钮、批量维护、状态查询或公开恢复 HTTP 接口。
- 新账号体系、所有权模型、令牌和鉴权实现；接口仍定位于受信任内部管理场景。
- 延长有效期、允许过期后状态维护、修改原始 URL、删除映射或重新发号。
- 重复操作返回成功、自动翻转状态、客户端业务版本检查或请求幂等键。
- 后台持续重试、持久补偿任务、消息队列和应用重启后的自动恢复。
- Redis 自动故障切换、旧快照自动恢复、缓存协议改版及新的流量治理或监控平台。
- 改变创建接口的同步重试策略或重构与本需求无关的业务模块。
