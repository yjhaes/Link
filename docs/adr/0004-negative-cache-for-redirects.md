# 阶段 4：缓存短链接的跳转拒绝结果

阶段 3 只缓存可跳转映射，格式合法的短码在缓存未命中后，即使数据库结果是不存在、已过期或已禁用，也会再次查询 MySQL。阶段 4 的已确认目标是减少重复访问同一短码产生的数据库查询；不承诺阻止持续更换合法短码的扫描，也不承诺所有实例及故障场景下的并发访问总共只查询一次数据库。

## 已确认的范围

- 缓存 MySQL 成功查询后得到的三类跳转拒绝结果：不存在、已过期、已禁用，分别保持 `404 LINK_NOT_FOUND`、`410 LINK_EXPIRED`、`403 LINK_DISABLED` 的区别。不能把它们合并为一种没有业务含义的空值。
- 格式非法的短码继续在访问 Redis 和 MySQL 前被拒绝。
- 三类拒绝结果分别配置 TTL 上限：不存在默认 30 秒、已禁用默认 15 秒、已过期默认 5 分钟；缓存命中不续期。写入时对正缓存及三类拒绝结果随机缩短配置时长的 0%～10%；限时正缓存仍取抖动后 TTL 与业务剩余有效时长的较小值，不能超过业务过期时间。抖动用于分散部分集中到期，不能解决单个热门 Key 的击穿或 Redis 整体不可用。
- 已禁用结果携带业务过期时间，缓存命中仍检查业务是否到期；到期时返回 `410`，保留过期优先于禁用的判断顺序，不能因 `403` 的缓存 TTL 尚未结束而继续返回 `403`。
- 创建或重新启用成功后，后续请求必须立即看到新状态；不接受迟到的旧拒绝结果回填后再等待 TTL 过期。后续请求指操作报告完成之后才开始的请求；与变更重叠的旧请求可以按此前读到的状态完成，后续新的合法变更及自然过期仍正常生效。
- 保留多个应用实例共享一个 MySQL 主写库及 Redis 的部署范围。创建和启用状态维护必须遵守同一缓存协调流程；维护可以保留 SQL 步骤，但需要受控的完成步骤，不能仅凭 SQL 提交就认为操作完成。不要求新增公开维护 API。
- 只有数据库提交并完成缓存协调后才报告操作完成。协调失败时明确说明数据库可能已经变更、完成状态尚未确认，需要恢复或重试协调；已提交的数据不能被描述为已回滚。已提交创建的恢复方式见下文，不能直接把重复创建请求当作协调重试。
- 本阶段不实现 Bloom Filter；文档说明其适用条件、误判、删除限制及完整初始化和同步的要求。
- 本决策增补并部分替代 [ADR-0003](0003-redis-cache-aside-for-redirects.md) 的拒绝结果缓存、缓存格式与 TTL、变更协调、完成状态及请求合并规则；未被本 ADR 替代的 Cache Aside、MySQL 权威数据源及业务过期判断等基础规则继续沿用。

## 已确认的读写协调方案

每个缓存条目携带版本标识。读取未命中时先取得当前版本再查询 MySQL；回填通过 Redis 原子操作校验版本，仅当仍匹配时写入。数据库变更提交后更换版本并清除缓存结果，确认协调成功后才报告操作完成。版本与结果保存在同一个有 TTL 的条目中，不永久保存所有访问过的短码；条目丢失时旧回填必须失败，重新初始化不能复用旧版本。

该协议约束所有缓存结果写入，包括正值、拒绝结果及由业务过期产生的结果更新；不把它描述为 MySQL 与 Redis 的原子事务。版本校验阻止旧结果回填，但不减少同一时刻的数据库查询，也不自动解决缓存击穿。

缓存未命中、无业务结果的版本占位、可跳转、不存在、已过期、已禁用必须能够被准确区分；占位用于协调，不是 `404` 结果。新结构需要使用新的缓存格式版本，所有参与保证的实例都使用同一协议。阶段 3 的两字段 `v1` 格式不能被假定已经支持这些状态。

## 已确认的故障边界

即时可见要求适用于同一 Redis 主实例、已确认协调结果未丢失的运行过程。临时不可达时读请求回源 MySQL；重启、恢复旧备份或切换实例时，先停用原缓存，完成清理重建后再恢复缓存使用。不承诺在丢失已确认写入、整体恢复旧快照或自动故障切换时自动保持该保证；这些情况下缓存值及版本都可能一起回滚。

## 已确认的缓存击穿方案

采用每实例内的请求合并：按“短码＋当前版本”共享一次正在进行的加载，正常的一轮同码、同版本并发 miss 由一个请求查 MySQL，其余请求等待并复用结果。不同实例允许各回源一次；本阶段不引入跨实例互斥回源的 Redis 锁。

不能只按短码共享任务，否则操作完成后的新请求可能加入旧版本任务并得到旧的 `404` 或 `403`，即使旧缓存回填已被版本检查拒绝也无法避免该错误。版本无法确认时不复用可能跨越变更的共享任务。共享结果仍由各请求检查业务过期边界，不能在等待期间到期后继续返回 `302` 或 `403`。

同码的不存在、已禁用等拒绝结果缓存到期时也适用该机制；持续更换不同短码的扫描不能靠同码请求合并解决。加载成功或失败后应清理对应任务，不因一个等待者超时而取消其他请求使用的共享任务。

等待共享任务的上限可配置，默认 200 毫秒。超时后重新读一次缓存，仍未命中则独立查询 MySQL，允许重复回源；不能无限循环加入原任务。该等待预算只限制等待共享任务的时间，不是整个 HTTP 请求的耗时上限，也不代替数据库查询超时。数据库查询失败沿用 `500`，不能写成拒绝结果缓存；共享任务失败后应允许后续请求重新加载。

## 已提交创建的协调恢复

映射创建已成功提交、但 Redis 协调超时或失败时，返回专门的 `503` 部分完成响应，携带已保存的短码并说明“数据库创建已提交，缓存协调未确认”，同时记录可据短码定位的日志。协调未确认不等于确定未执行：超时的 Redis 操作可能已经生效，因此恢复操作应允许安全重复执行。

维护者通过受控的内部步骤按同一短码只重试缓存版本更新及结果清除，不重新发号、不再次插入映射，也不凭旧请求结果重写启用状态；协调确认后才报告该操作完成。重新启用的协调恢复同样不再次修改数据库状态，仅重试协调。

当前 API 错误模型只有 `code` 和 `message`，实施时需要新增能表达上述部分完成结果的专门响应及恢复入口。本阶段不增加客户端请求幂等键或持久化恢复任务表；网络响应完全丢失后，重复 POST 仍可能创建另一条映射，不承诺自动识别原创建。相同原始 URL 可以对应多条独立映射的现有语义不变。

## 穿透、雪崩与热点 Key 的边界

- 非法格式：继续由 4 至 8 位 Base62 格式校验在 Redis 和 MySQL 前拒绝。
- 同一码重复访问：不存在结果缓存直接减少重复查询；已过期和已禁用映射虽然仍在数据库，也通过各自的跳转拒绝结果缓存减少回源，不能把它们描述为数据库不存在。
- 不断更换合法但不存在的短码：每个新码仍可能查询一次 MySQL，也会写入新的缓存条目。短 TTL 减少存留时间，不等于严格内存上限或限流；版本占位也须有限 TTL，不能永久积累历史访问集合。
- 集中到期：采用已确认的 TTL 抖动，分散部分到期时间；单个热门 Key 的并发 miss 由实例内请求合并缓解。
- Redis 整体不可用：保留短超时、回源及错误日志，不承诺数据库能承受全部流量；实例内合并也不是全局数据库限流器，版本无法确认时不能复用可能过时的任务结果。
- 正常命中的热点 Key：关注访问量、请求延迟、数据库回源量、Redis 超时及缓存内存，暂不实现长期本地缓存或 Key 拆分。本阶段不引入 Sentinel／Cluster、自动预热、后台刷新、专门限流或熔断机制。

## Bloom Filter 与面试知识

本阶段的主要验收目标是减少同一码重复查询，拒绝结果缓存已直接覆盖该目标，因此暂不实现 Bloom Filter。将来若大量不同的无效短码持续回源并形成可观测的数据库压力，再评估过滤器与限流；不能仅因项目已有 Redis 就加入过滤器。

Bloom Filter 以较小空间表示集合，能够过滤未进入负缓存的无效短码，但需要设置容量和误判率，并维护历史初始化、新建同步、完整性及恢复流程。回答“可能存在”不代表能够跳转；误判会让不存在短码继续查缓存或数据库，最终仍返回 `404`，不会直接返回 `302`。“确定不存在”的结论只适用于已完整、正确加入且未损坏的集合，漏加新短码或初始化未完成可能在系统层面错误拒绝真实映射。

普通 Bloom Filter 不支持安全删除单个成员，不能直接清除共享位。将来删除映射后，可保留过滤器中的历史成员，由数据库确认不存在并建立 `404` 缓存；必要时重建过滤器。残留成员与哈希碰撞误判都可能增加回源，但不会赋予跳转能力。Counting Bloom Filter、Cuckoo Filter、跨实例互斥回源、逻辑过期、后台刷新及自动故障切换可作为面试扩展知识理解，本阶段不实现。当前没有删除 API，本阶段也不新增；将来增加删除操作时，需要参与已确认的受控协调流程。

## 验收测试设计

测试是后续实现的验收计划，本轮不编写或运行实现测试。

| 场景 | 应证明的结果 |
| --- | --- |
| 格式非法 | 返回现有 `404`，Redis、MySQL 和任务合并器都不被调用。 |
| 三类拒绝结果 | 首次 miss 查询并回填正确类型；后续命中分别返回 `404/410/403`，不查 MySQL。 |
| 正常跳转回归 | hit 不查 MySQL；miss 查询后回填；保持 `302`、`Location` 与 `Cache-Control: no-store`。 |
| TTL 与抖动 | 使用可控随机值验证 0% 和 10% 两端及范围，命中不续期；真实 Redis TTL 在对应上限内，并为执行耗时留合理余量。 |
| 业务过期边界 | 使用可控时钟覆盖到期前与到期当刻；正值及已禁用结果在等待期间到期后都返回 `410`，不继续返回 `302/403`。 |
| 拒绝缓存自然到期 | 缓存到期后再次回源，并重新建立当前结果；与业务过期相区分。 |
| 同码实例内并发 miss | 无变更、无超时且正常回源的一轮同版本请求合并为一次 SQL；测试控制请求交叠，不靠偶然调度或所有响应相同来推断合并成功。 |
| 不同码并发 | 两个短码能够同时查询数据库，证明没有用一个全局锁串行化。 |
| 共享任务失败与清理 | 数据库失败仍为 `500`，不写拒绝缓存；任务完成或失败后清理，后续请求能够重试。 |
| 等待超时 | 仅超时的等待者重读缓存或独立回源；不取消共享任务，允许数据库查询次数增加，不无限重试等待。 |
| 迟到旧回填 | 在旧查询之后暂停任务，创建／重新启用并完成协调，再恢复旧回填；版本不匹配使回填失败，完成后开始的请求使用新状态。 |
| 新旧任务隔离 | 新版本请求不加入旧版本任务；与旧任务返回的 `404/403` 隔离，而不只检查 Redis 中没有旧值。 |
| 占位或条目丢失 | 未填充占位不返回 `404`；条目过期／被淘汰后，旧任务不能重建旧版本或无条件回填，新版本仍能正常加载。 |
| 多实例 | 独立应用实例共享 MySQL 和 Redis，验证版本协议跨实例生效；每个实例允许各回源一次。不能仅凭同 JVM 中共享的静态任务表宣称跨进程有效。 |
| Redis 与损坏值 | 读失败、超时、写失败及损坏／未知格式都按既定语义处理；不能误当作不存在，也不能使用无法确认版本的旧任务。用少量真实 Redis 断连或超时验证降级。 |
| 部分完成与恢复 | MySQL 确已提交后注入协调失败，响应 `503` 且有短码；按该短码恢复协调，数据库映射及发号次数不增加，协调成功后新请求可见。覆盖协调已执行但响应超时后的重复恢复。 |
| 数据库未提交 | 创建数据库失败时不宣称已创建或协调待完成，保持现有失败语义；查询失败不建立负缓存。 |
| 恢复运行过程 | 以受控步骤停用旧缓存并清理后恢复按需回填；不把直接恢复旧快照描述为自动维持即时可见。 |
| 大量不同无效短码 | 用少量确定数据说明新码仍会回源、缓存条目均有有限 TTL；不以此证明抗攻击能力或目标 QPS。 |

服务层用可控时钟、随机源、查询计数和并发同步点验证行为；少量真实 MySQL／Redis 集成测试验证序列化、实际 TTL、原子版本校验及故障降级。并发测试使用闩锁等同步点控制先后，不用长时间 sleep 模拟竞态；TTL 到期可在测试中缩短配置，以有界等待验证。至少一项关键一致性验证使用独立进程或等效隔离的应用实例，避免误用 JVM 全局状态。

这些测试验证正确性与查询减少，不代替性能压测，也不要求模拟亿级流量。没有实现 Bloom Filter，因此不为它编写实现测试；理解误判与删除边界即可。

## 与阶段 3 的冲突

ADR-0003 接受数据库提交后删除缓存、删除失败仍算变更成功，以及旧结果并发回填后由 TTL 兜底。阶段 4 对创建与重新启用选择了即时可见要求，因此不能直接沿用上述规则并宣称已获得保证。当前重新启用通过直接 SQL 与显式删除缓存维护，没有能约束所有并发读写的应用内变更入口；已确认改为受控的缓存版本更新流程，数据库提交及协调完成应分别报告。
