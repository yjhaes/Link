# 阶段 2：自增 ID 经有界双射后编码为 Base62 短码

> 当前实现说明（2026-10-01）：当前代码已包含独立 MySQL 发号、固定有界双射、4 至 8 位 Base62 编码及仅对短码主键冲突重试一次的流程，`schema.sql` 也已包含短码列调整。发号契约和编码规则位于 `shortcode`，数据库实现位于 `persistence`。下文关于第一阶段代码尚未改动的表述保留为原决策背景；实现现状见 [架构说明](../architecture.md)，本说明不替代测试验收。

本项目的短码是公开标识，不承担授权或保密职责。已确认混淆只需让普通用户看不出自增顺序，允许短码被分析推算，不把它当作防枚举措施。短码长度为 4 至 8 位，并将完整短码写入数据库；按累计创建 1000 万条、未来可能上亿条、多个应用实例共享一个 MySQL 主写库来评估。本决策由独立的 MySQL 自增流水表分配 ID，先对 ID 作固定的有界双射，再将结果编码为 Base62。它取代 [ADR-0001](0001-short-code-as-primary-key.md) 中的随机短码生成方式，保留短码作为映射表主键；当前第一阶段代码尚未改动。

## 编码与长度边界

- 固定 Base62 字符表 `0123456789abcdefghijklmnopqrstuvwxyzABCDEFGHIJKLMNOPQRSTUVWXYZ`。字母和数字适合放在 URL 路径中，但 Base62 只负责缩短数字的文本表示，本身不产生唯一性或安全性。
- 令 `M = 62^8 = 218,340,105,584,896`。对 `1 ≤ id ≤ M`，选定并固定参数 `a`、`b`，其中 `0 < a < M`、`0 ≤ b < M` 且 `gcd(a, M) = 1`；计算 `v = (a × (id - 1) + b) mod M`，先取规范的 `Base62(v)`，若不足 4 位就在左侧补字符 `0` 至 4 位，其余长度不补。
- 本提案选用 `a = 134941606358707`、`b = 90439432943237`。`a` 为奇数且不能被 31 整除，因此与 `62^8 = 2^8 × 31^8` 互质；这两个参数没有保密意义。固定测试向量：`id = 1 → pGeGLWSx`、`id = 2 → 1ZXuEkNa`、`id = 23 → G8o4qYn`、`id = M → NmvSTyXU`。
- 乘数 `a` 与模数 `M` 互质，使上述映射在允许的 ID 范围内一一对应；`0 ≤ v < M` 保证原始 Base62 结果最长 8 位，补齐规则保证最短 4 位。被补齐的结果以 `0` 开头，原本至少 4 位的规范 Base62 结果不会以 `0` 开头，因此补齐不引入碰撞。超过 `M` 的 ID 必须明确使创建失败，不能取模复用旧短码。实现应使用不会在乘法中溢出的运算，再验证 4 至 8 位结果。
- 例如映射结果 `v = 1` 时，Base62 为 `1`，对外短码是 `0001`；`v = 62^3` 时，Base62 本来就是 `1000`，无需补齐。这是最小长度规则，不是固定补到 8 位。
- 这是固定规则下的**确定性打乱**，不是每次独立随机发号，也不是加密。知道规则的人仍能推算其他短码。8 位码占可用 4 至 8 位空间的约 98.4%；用户明确接受长度只受 4 至 8 位边界约束，不要求各种长度经常出现。按上述参数计算前 1000 万个 ID，4、5、6、7、8 位短码分别有 1、42、2558、158689、9838710 个。
- 仅有 `gcd(a, M) = 1` 保证唯一，不能保证外观被打乱；例如 `a = 1`、`b = 0` 会得到 `0000`、`0001`、`0002` 等连续短码。本提案参数的相邻 ID 示例显示外观不呈现直接自增顺序，但仿射映射仍可由已知相邻样本推算，不能据此宣称降低枚举风险。
- 开发期没有需要保留的真实短链接，可以调整编码规则并清理开发数据；对外发布短链接后，字符表、参数和补齐规则保持稳定，多个应用实例使用同一套规则。将来若改变规则，已入库的旧短码仍可跳转，但新码可能与旧码冲突；当前阶段不设计新旧规则共存机制。

## 持久化、唯一性与跳转

- 新增追加式 MySQL 发号表，以 `BIGINT AUTO_INCREMENT` 为主键；每次创建先向它插入一行并取得新 ID，再计算最终短码。发号表的行随创建次数累积，回滚也可能消耗自增值；不引入 Redis 发号器或单行计数器。
- 独立发号表是为了同时满足“短码由 ID 推导”和“映射首次插入就有最终短码且 `NOT NULL`”：同一映射行的数据库自增 ID 只能在插入后由应用取得，无法用于应用在该次插入前计算短码。
- 短链接映射表继续以 `short_code` 为主键，不保存发出的数字 ID。实施时将短码列调整为可容纳 4 至 8 位的 `VARCHAR(8) NOT NULL`，沿用 `utf8mb4_bin` 排序规则精确区分大小写；首次插入映射时即写入最终短码。先插入 `NULL` 再回填的草案已被否决。
- 发号和建立映射分别提交，不使用跨两表的创建事务。发号模块只负责分配唯一正整数；拿到已提交的 ID 后，计算短码并由映射模块单独插入映射。若应用在两步之间退出，或映射插入失败，发号表中保留未使用的 ID，短链接映射不存在；允许这种空洞，也不回收或复用 ID。唯一性来自发号表自增 ID、固定双射及映射表主键，而不是事务边界。
- 分别提交缩短每一步的事务范围，但不能据此推断吞吐一定更高：普通自增插入的发号锁原本就不会持有到整个创建事务结束，两个独立提交还可能增加日志刷盘。若以后有明确吞吐目标，应在同一环境压测，而不是把事务拆分当作性能结论。发号与映射是同一应用内的职责划分，当前不需要拆成独立服务。
- 发号表主键保证发出的 ID 唯一，双射保证固定规则下不同 ID 的短码不同，映射表的短码主键对编码错误、配置不一致或迁移错误作最终兜底。当前随机短码方案最多尝试插入 4 次；新方案仅在短码主键冲突时重新发一个 ID 并重试一次，即总共最多插入映射 2 次。第一次冲突就记录异常，第二次仍冲突则创建失败并排查；即使重试成功也不能把首次冲突当作正常随机碰撞。其他数据库错误不进入短码冲突重试。

- 若未来要求真正难以预测的短码、有独立数据库写入节点，或不能接受发号与映射两次插入，应重新评估机制。有界双射仅解决外观顺序，不作为防枚举或访问控制措施。

## 取舍过的方案

| 方案 | 本项目的取舍 |
| --- | --- |
| 现有随机短码 | 一次映射插入即可完成创建，最简单；短码不由 SQL ID 推导，需保留正常碰撞重试。 |
| UUID 截断 | 截断后仍要处理碰撞，相比直接生成定长随机短码没有明显收益。 |
| 直接 Base62(ID) | 唯一且更简单，但外观直接暴露自增顺序。 |
| ID + Hashids | 可以混淆；固定实现和 ID 范围后也可验证长度，但本提案的 8 位边界与唯一性证明更直接。 |
| 自增 ID + 随机后缀 | 增加猜测成本并占用长度；项目只要求外观不连续。 |
| Snowflake + Base62 | 适合多节点独立发号；共享 MySQL 已分配唯一 ID，不需要节点编号和时钟回拨处理。 |

## 验证边界

- 编码：用固定向量锁定参数与字符表，验证 `id = 1`、`M`、`M + 1`，以及映射值 `v = 0` 和 `62^3`、`62^4`、`62^7` 两侧的长度边界；确认 4 至 8 位、乘法不溢出。唯一性依靠双射证明，不靠随机抽样。
- 数据库与并发：验证首次插入即有完整短码，`NOT NULL` 主键区分大小写；多实例同时创建无重复；发号后映射失败留下未使用 ID；只对短码主键冲突重新发号重试一次。跳转校验改为 4 至 8 位 Base62，并覆盖 3/9 位拒绝、大小写及已有的过期和禁用行为。

面试重点是解释双射与数据库主键各自保证什么、8 位上限如何证明、为什么允许发号空洞、分开提交的失败语义，以及为什么不选 Snowflake。外观混淆不能当作防枚举措施；并发正确性也不能代替吞吐压测。

## 实施注意

当前 `schema.sql` 使用 `CREATE TABLE IF NOT EXISTS`，实施时仅编辑建表语句不会改变已有表；由于开发数据不需保留，实施阶段可明确重建开发表并调整现有建表脚本，不需要设计新旧短码兼容迁移。当前第一阶段代码尚未改动。
