# 短码生成与数据库

返回 [面试导航](README.md)。先掌握唯一性和失败语义，再展开数学、事务和索引；不要求把固定参数背下来。

## 必会回答

### Q1. 为什么用 Base62？

Base62 使用数字、大小写字母共 62 个字符表示整数，适合短码路径。本项目固定字符表为 `0123456789abcdefghijklmnopqrstuvwxyzABCDEFGHIJKLMNOPQRSTUVWXYZ`。

它是编码，不是加密，也不是唯一 ID 生成器。对同一个整数会得到相同结果；不同 ID 能否得到不同短码，还取决于前面的发号和映射规则。

### Q2. 项目如何保证短码唯一？

三个层次分别负责不同问题：

1. MySQL 发号表以自增主键分配唯一正整数。
2. 固定有界双射把允许范围内的不同 ID 映射为不同整数，再编码成短码。
3. 映射表的 `short_code` 主键兜底编码、配置或迁移错误。

不是“先查数据库有没有这个码，再插入”：两个请求可能同时查到不存在，最终约束应由数据库完成。

### Q3. 当前编码是不是直接 Base62(ID)？

不是。令 `M = 62^8`，先计算：

```text
v = (a × (id - 1) + b) mod M
shortCode = Base62(v)，不足 4 位左补 0
```

其中 `1 ≤ id ≤ M`，`gcd(a, M)=1`，参数固定。互质使乘法在模 M 的范围内可逆，平移不改变一一对应关系；Base62 和补齐规则再保持可区分。代码使用 `BigInteger` 计算，避免中间乘法溢出。

实际固定向量 `id=1 → pGeGLWSx`，不能把教材中 `Base62(1)=1` 当作当前最终短码。长度是 4～8 位，但并不均匀分布，大部分可能是 8 位；不承诺码长随创建数量逐步增长。

证据：[编码器](../../src/main/java/com/example/shortlink/shortcode/PermutedShortCodeEncoder.java)、[编码决策](../adr/0002-permuted-auto-id-base62.md)。

### Q4. 为什么不用 UUID 截断、Snowflake 或直接哈希 URL？

| 方案 | 应解释的取舍 |
| --- | --- |
| UUID 截断/随机短码 | 截断或随机取值后仍有碰撞概率，需要唯一约束和重试；随机方案本身可更简单 |
| URL 哈希截断 | 有碰撞；相同 URL 默认得到同值，不直接符合独立映射语义 |
| 直接 Base62(ID) | 唯一且更简单，但外观显示递增顺序 |
| Snowflake | 适合独立节点发号；当前多个应用实例共享 MySQL，已有自增 ID，可不引入节点号和时钟处理 |

不要说这些方案“不好”。当前选择满足固定长度上限与外观不连续，代价是独立发号表和两次插入；双射也不提供防枚举安全性。

### Q5. 已经有双射，为什么还处理主键冲突？

理论保证有前提：允许范围、参数、字符表和补齐规则必须一致。实现错误、不同版本混用或迁移问题仍可能违背前提。数据库主键提供最后的防线。

只对短码主键冲突重新发号重试一次，即最多两次映射插入；首次冲突就值得排查，不当作普通随机碰撞。其他唯一约束或数据库异常不进入该重试。

### Q6. 发号成功但保存映射失败怎么办？

ID 留下空洞，不回收复用；该 ID 不自动形成可访问的短链接。发号与映射分别提交，是已接受的失败语义。

自增值不是业务成功计数；不要用它统计有效短链接数量。分开提交也不自动意味着更快，需要实际测量两次插入和提交的代价。

## 事务与状态维护

### Q7. 为什么创建入口使用 NOT_SUPPORTED？

创建通过 Spring 管理的入口挂起调用者事务，使发号和映射插入按当前非事务调用路径分别提交。这样不会出现“缓存协调已报告成功，外层数据库事务后来回滚”的结果。

这是当前 MyBatis/Spring 装配下的行为，不是“加了这个注解，一切 JDBC 都自动提交”。必须结合调用入口、连接和 Mapper 的实际事务参与情况解释。

### Q8. 启禁用为什么要行锁？

`ShortLinkStateService` 在独立事务内按短码主键 `SELECT ... FOR UPDATE`，取得锁后判断映射、有效期和重复目标，再只更新 `enabled`。竞争操作按实际锁/提交顺序处理，不先读取旧状态再各自覆盖。

拿到锁后才检查时钟，因为等待期间链接可能过期。重复启用/禁用返回 409，过期后状态操作返回 410；这不是任意 PUT 都重复返回成功的接口。

锁属于事务，事务结束后释放；本机 Java 锁无法约束另一应用进程的数据库写入。锁的具体范围仍取决于索引和查询条件，不能笼统说所有查询只锁一行。[MySQL 锁定读说明](https://dev.mysql.com/doc/refman/8.4/en/innodb-locking-reads.html)。

### Q9. REQUIRES_NEW 与程序式事务用在哪里？

状态用例外层入口是 `NOT_SUPPORTED`，内部 `TransactionTemplate` 使用 `REQUIRES_NEW` 执行读锁和更新。模板返回后才进行 Redis 协调，明确区分数据库提交与缓存同步。

`REQUIRES_NEW` 是独立物理事务，不能与复用同一事务保存点的 `NESTED` 混淆。它有连接资源成本，并非所有方法都适合使用。[Spring 6.2 事务传播说明](https://docs.spring.io/spring-framework/reference/6.2/data-access/transaction/declarative/tx-propagation.html)。

### Q10. 为什么不在事务内部同步 Redis，失败就一起回滚？

Redis 不参与这里的 MySQL 本地事务。Redis 命令可能已经执行但响应超时，数据库随后回滚并不能自动撤销 Redis 状态；把网络调用放在持锁事务里还会延长锁占用。

当前先确认数据库提交，再轮换缓存版本，协调失败报告专门的部分完成 503。状态同步最多三次，等待 50/100ms，只重试缓存协调，不重复修改数据库。

证据：[状态用例](../../src/main/java/com/example/shortlink/service/ShortLinkStateService.java)、[Mapper](../../src/main/java/com/example/shortlink/persistence/ShortLinkMapper.java)、[状态决策](../adr/0005-enabled-state-api.md)。

### Q11. @Transactional 什么时候可能不生效？

本项目需通过 Spring 管理的代理入口调用。默认代理模式下，同一对象内部直接调用自身方法，不会自动经过事务代理；测试直接 `new` 一个对象也不证明 Spring 事务装配生效。

因此纯用例测试与真实 Spring/数据库测试负责不同证据。不要把私有方法随手加注解，或把 Redis/MQ 失败全部解释成数据库事务回滚。[Spring 注解事务说明](https://docs.spring.io/spring-framework/reference/6.2/data-access/transaction/declarative/annotations.html)。

## 表结构与 SQL 追问

### Q12. 三张表各自负责什么？

| 表 | 关键约束/索引 | 用途 |
| --- | --- | --- |
| `short_code_issuance` | 自增数字主键 | 分配 ID，不等同映射成功数量 |
| `short_link` | `short_code` 主键，`utf8mb4_bin` | 按完整短码定位映射，精确区分大小写 |
| `short_link_visit_log` | 自增行 ID；`event_id` 唯一键；统计、明细、清理索引 | 去重保存访问事件与在线查询 |

映射以 4～8 位短码作主键，没有另存一个数字 ID 和短码唯一索引。短码是公开业务标识，主键与对外标识绑定，今后改形式有迁移成本。

InnoDB 使用聚簇索引组织数据，二级索引包含主键信息。按打乱后的短码插入不具备数字自增的相同顺序特征，选短码主键是查找和结构取舍，不能无数据声称比自增主键全面更快。[MySQL 索引说明](https://dev.mysql.com/doc/refman/8.4/en/innodb-index-types.html)。

### Q13. 统计联合索引为什么这样排列？

现有索引包括 `(short_code, stat_date, visitor_key_version, visitor_hash)`：查询先限定短码，再按日期范围过滤，访客版本和摘要用于范围 UV 去重。明细索引是 `(short_code, occurred_at, id)`，配合短码、发生时刻和行 ID 倒序；清理索引是 `(stat_date, id)`。

字段顺序从实际过滤和排序需求出发。实际 SQL 还过滤 `occurred_at`，不能把统计索引直接说成完全覆盖查询，也不能说有索引就不会扫描或排序。进一步优化需在隔离环境查看 EXPLAIN、数据分布、扫描量和执行耗时；本轮没有新增执行计划证据。

### Q14. 为什么访问明细用游标而非深 OFFSET？

明细按 `(occurred_at DESC, id DESC)` 排序。下一页使用上一页最后一条的位置：

```sql
AND (occurred_at < ? OR (occurred_at = ? AND id < ?))
ORDER BY occurred_at DESC, id DESC
LIMIT ?
```

行 ID 打破同毫秒时间相同的平局。游标绑定短码和日期范围，不能复用于另一查询；每次读取有自己的数据库快照，不能宣称跨所有分页请求冻结整个数据集。游标也不用于授权，管理接口仍先鉴权。

证据：[schema.sql](../../src/main/resources/schema.sql)、[统计查询实现](../../src/main/java/com/example/shortlink/stats/query/MySqlVisitStatsQuery.java)。
