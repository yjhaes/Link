# 项目介绍与设计取舍

返回 [面试导航](README.md)。本篇先解决“项目做了什么、为什么这样做、一次请求如何走完”。回答示例可按本人实际承担的工作改写，不虚构用户量、上线规模或团队贡献。

## 开场介绍

### 30 秒版本

> 这是一个面向 Java 后端学习和实习展示的短链接服务，支持匿名创建永久或限时短链接、跳转、内部启禁用和访问统计。MySQL 保存权威映射，Redis 做跳转缓存和分组限流，RabbitMQ 异步处理访问事件。重点是短码唯一性、缓存失效时的并发与一致性，以及统计重投去重。当前是本地单应用，不宣称生产高可用。

### 2 分钟版本

> 用户提交原始 URL 后，系统从 MySQL 取得自增 ID，按固定双射规则打乱，再编码为 4～8 位 Base62 短码。映射以短码为主键保存，数据库提交后完成缓存版本协调才报告创建成功。
>
> 跳转先校验格式和限流，再读 Redis；缓存未命中时查 MySQL，并根据读取时的版本条件回填。除了正常映射，也缓存不存在、已禁用和已过期的结果。同码并发 miss 在实例内合并加载，TTL 加抖动，实际回源还有并发准入。每个请求仍检查业务有效期。
>
> 正常 GET 跳转决定后生成独立访问事件，通过有界本地交接交给后台发布，MQ 消费者同步写 MySQL。用 eventId 唯一键防止重投重复入账，查询基于已记录事件统计 PV/UV。统计允许漏记，MQ 故障不阻塞核心跳转；测试关注竞态、失败边界和真实接口结果。

## 必会回答

### Q1. 三个中间件分别负责什么？

| 组件 | 职责 | 不应混淆的地方 |
| --- | --- | --- |
| MySQL | 发号、权威短链接映射、已记录访问日志与统计查询 | 缓存命中不能取代业务有效期校验 |
| Redis | 跳转结果缓存、版本协调、按请求组限流 | 缓存故障和限流故障策略不同 |
| RabbitMQ | 将统计发布/消费工作移出 HTTP 线程，缓冲部分统计积压 | broker 确认不是数据库已保存 |

这是一个 Spring Boot 进程内的职责划分，没有拆成三个业务服务。页面也由同一应用提供。

### Q2. 一次创建如何走完？

```text
创建限流 → URL/有效时长校验 → MySQL 发号 → 双射和 Base62
→ 插入映射并确认提交 → 轮换 Redis 版本 → 返回 201 与短链接
```

发号与映射插入分别提交，允许 ID 空洞。只有短码主键冲突才重新发号重试一次，其他数据库错误不当作短码碰撞。数据库已提交而 Redis 协调未确认时，返回带短码的专门 503。

证据：[创建用例](../../src/main/java/com/example/shortlink/service/ShortLinkCreationService.java)。

### Q3. 一次跳转如何走完？

```text
短码格式校验 → 跳转限流 → Redis 读取
→ 命中使用结果 / miss 合并加载并查询 MySQL
→ 按版本回填 → 逐请求检查有效期和状态 → 302 + Location
→ 正常 GET 的访问事件尝试交给统计模块
```

拒绝结果为不存在 404、已过期 410、未过期但已禁用 403。统计采集发生在正常跳转决定后，不等待后台统计网络或 SQL；共享缓存加载的等待则仍可能占用当前 HTTP 线程。

证据：[跳转用例](../../src/main/java/com/example/shortlink/service/RedirectService.java)、[控制器](../../src/main/java/com/example/shortlink/api/ShortLinkController.java)。

### Q4. 为什么使用 302，而不是让浏览器长期记住跳转？

链接有过期和启禁用状态，需要请求回到服务端重新判断。当前采用 302，并显式返回 `Cache-Control: no-store`；若客户端长期缓存重定向，可能绕开状态变化和本次访问采集。

不要只说“302 一定不缓存”：项目通过响应头表达缓存策略。HTTP 语义可参考 [RFC 9110](https://www.rfc-editor.org/rfc/rfc9110.html#section-15.4.3)，实际行为以控制器及响应测试为准。

### Q5. 同一个原始 URL 为什么能创建多个短链接？

项目把“一次创建产生的映射”作为独立记录，原始 URL 不设唯一约束。不同映射可以有不同有效时长、启用状态和访问统计。这是业务选择，不是遗漏去重。

当前 POST 没有客户端幂等键。重复提交或响应丢失后重试可能新增映射，不能从“URL 相同”推断系统会返回旧短码。

### Q6. 过期、禁用和缓存过期有何区别？

| 状态 | 含义 | 判断方式 |
| --- | --- | --- |
| 业务已过期 | 有效期终点已到达 | 每个请求比较 `expiresAt` 与时钟，到期当刻拒绝 |
| 已禁用 | 管理者主动停止使用，可以重新启用 | 查询映射或使用缓存快照中的业务结果 |
| 缓存过期 | Redis 副本达到 TTL | 缓存 miss 后回源，不代表业务链接失效 |

到期优先于禁用；永久链接的业务到期时间为空，但缓存仍有有限 TTL。

### Q7. 为何不采用微服务或独立前端？

目前只有短链接这一项业务，单应用便于本机运行、调试和交代完整链路。引入跨服务调用、账号平台和独立前端构建，会扩大部署与维护成本，当前没有相应需求或规模证据。

RabbitMQ 已展示异步边界，不需要再把发布者和消费者拆成微服务来证明会用 MQ。

## 进阶追问

### Q8. 内部管理接口怎么保护？

配置管理令牌后，用且只用一个 `X-Internal-Token` 头；未配置时管理接口关闭并返回 404，已开启但令牌无效返回 401。鉴权先于限流和请求参数/请求体解析，拒绝请求不进入业务。

这不是完整账号体系，没有用户登录、角色或链接归属模型。管理端口仅绑定本机，其健康/指标边界与业务令牌不同。

证据：[管理拦截器](../../src/main/java/com/example/shortlink/api/management/InternalManagementAccess.java)、[API 契约](../入门与使用/api.md)。

### Q9. 为什么没有把所有步骤放在一个事务里？

数据库事务能约束同一数据库连接上的工作，不能直接把 Redis 协调和 MQ 发布纳入 MySQL 的原子提交。项目分别表达“DB 提交”“缓存协调”“统计交接”等结果，不能用一个 `@Transactional` 宣称跨组件原子性。

映射写入与访问统计也不组成必须一起成功的业务事务：跳转优先，统计 best-effort。更强可靠性要改变需求，并讨论补偿、持久事件记录及运行成本。

### Q10. 你遇到的最难问题是什么？

选本人确实理解并参与的一项，用具体场景回答：

> 一个旧查询暂停后，另一个请求完成状态修改；如果旧查询再回填，即使改完已经删过 key，旧状态仍会回来。我把回填和加载任务都按缓存版本隔离，并控制请求交叠验证旧回填被拒绝、新请求不会加入旧任务。版本无法确认和等待超时仍有明确回源边界。

也可选“同事件落库后 ACK 丢失导致重投”“数据库提交成功却协调超时”，见其他专题。不要把没实现的 Redis Cluster 或 outbox 当作亲身解决的问题。

### Q11. 项目还可以怎么改？

先指出观察到的问题，再选变化，而不是列满新技术：统计若要求不漏记，评估持久事件交接；单实例热点压力明显，测量回源量再评估跨实例合并；创建写入成为瓶颈，测量 MySQL 发号和插入成本再改发号方式。

这些是扩展方向，不代表已实现、已有瓶颈或已证明性能收益。当前学习目标先是把现有链路讲清并验证。

### Q12. 为什么采用构造函数注入，并单独注入 Clock？

构造函数明确声明用例需要哪些依赖，便于检查职责和在测试中替换已有接缝。代码把时间判断交给 `Clock`，测试可以固定时刻或推进到过期边界，不依赖本机当前时间和长时间 sleep。

控制器负责 HTTP 表示，用例负责业务流程，缓存和数据库实现封装各自协议。不为每个类都额外加一个只透传的接口，也不把当前 service 宣称为与数据库完全无关的纯领域层。

### Q13. 两个 DataSource 怎么避免注错？

核心数据源保留主候选标记，统计配置提供另一个具名数据源；统计写入和查询通过 `@Qualifier("statsDataSource")` 明确选择。不能只靠变量名或“Spring 应该会猜对”，也不能让统计池意外接管核心 Mapper/事务。

装配测试核对 `JdbcTemplate`、事务管理器和两池的归属。两池的职责隔离仍不等于独立 MySQL，细节见 [当前架构](../架构与原理/architecture.md)和[统计装配测试](../../src/test/java/com/example/shortlink/stats/config/StatsConfigurationTest.java)。

## 复述检查

不用看稿解释：为什么同一 URL 可以对应多条映射；为什么 TTL 到期不等于链接失效；为什么 201、302、统计已保存分别表示不同结果。再从 [源码架构](../架构与原理/architecture.md)找到你刚才描述的入口。
