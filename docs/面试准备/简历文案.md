## 一、推荐版本（4 条）

> **短链接服务** ｜ 个人项目 ｜ Java 17 · Spring Boot 3.5 · MyBatis-Plus · MySQL · Redis · RabbitMQ ｜ 2026.09 – 2026.10
>
> 面向读多写少的跳转场景，独立完成创建、302 跳转、过期与启禁用、匿名访问统计的完整后端链路，共 8.4k 行主代码 + 8.0k 行测试代码（317 项 Java 测试全部通过，含 Testcontainers 真实设施用例）。
>
> - **短码生成**：基于 MySQL 自增发号 + 有界双射置换 + Base62 编码生成 4~8 位短码，以映射表主键兜底唯一性；发号与映射写入分别提交，仅对主键冲突重试一次，避免数据库已提交后缓存协调被外层事务回滚。
> - **缓存一致性**：跳转采用 Cache Aside，针对穿透/击穿/雪崩分别实现不存在·禁用·过期三类负缓存（区分 404/403/410 与独立 TTL）、按「短码 + 缓存版本」合并同码并发回源（`putIfAbsent` + `CompletableFuture`，等待预算 200ms）、TTL 随机抖动 0%~10%。针对“读旧值后暂停、写完再迟到回填”的竞态，改为提交后轮换版本、回填时用 Redis Lua 原子校验版本，拒绝旧结果写入。
> - **异步统计与幂等**：用有界本地队列 + RabbitMQ 把统计网络与 SQL 移出 HTTP 线程，以 UUID `eventId` + 数据库唯一键实现消费者幂等（重投不重复计 PV），双连接池隔离统计与核心链路，实现 PV/UV、日趋势与游标分页访问明细；明确统计 best-effort，MQ 故障不影响跳转。
> - **限流与故障隔离**：基于 Redis Lua 令牌桶按创建/跳转/管理写/管理查询四组限流（Lua 内完成取时、补充、扣减，避免并发放行最后一个令牌），并对实际跳转 SQL 设置每实例 4 并发准入；区分 429 与业务前 503，Redis 故障时创建拒绝、跳转降级查库且拒答不产生统计副作用。

## 四点五、容量数字的正确口径（能用什么、不能用什么）

来源：[测试证据运行报告](../测试与验证/summary.md)（运行 `20261006-210259-c11b6774`，源码 `af4876d`）。该报告使用严格门槛：成功率 ≥99.9%、成功响应 p95 ≤200ms、GET 还需发布/消费/写库全闭环且队列斜率 ≤0.1 条/秒；正式候选需三轮全通过 + 十分钟持续验证。

### 可以写的

> 单机 GET 回源路径在 **80 req/s 持续负载**下成功率 >99.9%（p95 10~12ms，含访问统计发布/消费/落库全链路闭环）。

这是 `verified-lower-bound`（已验证下界），有方法、有门槛、有重复轮次。**主动区分“已验证下界”和“真实最大值”是加分项**——它证明你懂压测方法论。

### 不能写的

| 想写 | 为什么不行 |
| --- | --- |
| “最高 110 req/s” | 110 是**未通过的探索上界**，三轮正式结果不一致 |
| “性能提升 X%” | 缺同一次运行的 A/B 对照组与命中率数据 |
| “承载 690 万请求/天”（80×86400） | 由速率外推日容量，报告未验证连续日负载 |
| “HEAD 缓存命中双 JVM 达到 80/s” | 该项 `inconclusive`，受负载发生器调度限制 |
| “缓存命中 p95 6.8ms” | 单次探索样本，未进正式三轮验证 |

80 req/s 本身已足以支撑“能扛住可观流量”的叙事，不需要放大成 110 或换算成天数。

### 两点使用前提

1. **测量时工作树不干净**（报告记录 `工作树干净: False`）。报告中“源码提交”与当前 HEAD 一致，但工作区有 `application.yml` 的本地修改。若该修改影响限流额度或并发准入，实测条件与默认配置并不等价。引用前先说明。
2. **原始证据文件不在仓库**：报告引用的 `capacity-results.json`、`manifest.json`、`samples.jsonl`、`requests-*.csv.gz` 等均不存在，`summary.md` 自身也未提交（`git status` 显示为未跟踪）。面试官要求看报告时你无法提供。**先从归档处找回这些文件并提交，再把这个数字写进简历。**

## 六、每条要能接住的追问

| 简历条目 | 至少能回答 |
| --- | --- |
| 短码生成 | Base62 为什么不保证唯一；双射为什么用互质参数；为什么允许发号空洞；主键冲突为什么只重试一次 |
| 缓存一致性 | 穿透/击穿/雪崩的区别与各自限制；为什么加载任务的 key 要带版本；迟到回填的具体时序；为什么延迟双删不够 |
| 异步统计 | 本地交接 / broker 确认 / MySQL 保存三个成功边界的区别；重复消费怎么发生；刷新为什么算两次 PV；为什么可能漏记 |
| 限流与并发 | 令牌桶与 Semaphore 的区别；为什么 Lua 里要读 Redis TIME；扣减超时为什么不重试；429 与 503 的语义差别 |
