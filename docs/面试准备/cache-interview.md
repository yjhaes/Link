# 缓存优化面试提纲

本项目已经实现穿透、击穿和雪崩场景的部分防护。面试按“问题是什么→项目怎么做→证据在哪里→还剩什么限制”回答；启动时不需要先读这份材料。

返回 [面试导航](README.md)。先掌握概念对照与一分钟介绍；请求共享使用到的 Java 工具见 [限流与 Java 并发](限流与Java并发.md)，受控并发怎么证明见 [测试与模拟面试](测试证据与模拟面试.md)。

## 先区分三种问题

| 问题 | 短链接中的例子 | 已实现的措施 | 限制 |
| --- | --- | --- | --- |
| 缓存穿透 | 反复访问数据库中不存在的短码，每次 miss 都查库 | 非法格式提前拒绝；不存在结果缓存；HTTP 跳转按连接对端 IP 限流 | 不断更换合法无效短码仍可能回源；没有 Bloom Filter |
| 缓存击穿 | 一个热门短码的缓存过期，交叠请求同时查库 | 按短码＋版本做实例内请求合并，共享一次正在进行的查询 | 不跨实例合并；等待超时或版本无法确认时允许额外查询 |
| 缓存雪崩 | 大量条目集中到期，或 Redis 整体不可用，大量请求转向数据库 | 业务结果 TTL 随机缩短 0%～10%；实际跳转 SQL 设置每实例并发准入，默认 4 | 抖动只能分散部分到期；准入不足返回 503，不保证所有请求成功或 Redis 高可用 |

三者可以一起发生，但措施不同：缓存不存在结果针对穿透，共享同码加载针对击穿，分散到期和限制整体回源压力针对雪崩。Redis 官方将热门 key 到期时并发回源称为 cache stampede，背景见 [Cache Aside 说明](https://redis.io/docs/latest/develop/use-cases/cache-aside/)。

## 一分钟介绍

> 跳转采用 Cache Aside，MySQL 是权威来源。除了正常映射，也缓存不存在、已禁用、已过期三类结果，减少同码重复回源。热门短码并发 miss 时，在单实例内按短码和缓存版本共享正在执行的查询；业务结果 TTL 加随机抖动，分散集中到期。Redis 故障时跳转降级查库，实际查询有每实例并发上限，避免无限增加回源。创建和启禁用提交后轮换缓存版本，回填用 Lua 检查版本，拒绝迟到的旧结果。这些措施有实例和故障边界，没有实现跨实例回源锁或 Redis 高可用。

这段介绍可拆成下面五组追问。无需把全部类名和运行参数背进开场。

## 1. 穿透：为什么缓存不存在结果？

第一次访问合法但不存在的短码，MySQL 查询得到不存在，写入 `NOT_FOUND` 结果；相同短码后续命中直接返回 404。默认 TTL 上限 30 秒，并加入抖动，命中不续期。

已禁用和已过期映射仍在数据库中，分别缓存 `DISABLED` 和 `EXPIRED`，不能都称为数据库不存在。它们的 TTL 上限分别为 15 秒和 5 分钟，HTTP 结果分别为 403 和 410。

**追问：负缓存会不会挡住刚创建或重新启用的链接？**

会有这种风险，因此创建或状态变更在数据库提交后轮换缓存版本、清除旧业务结果。旧请求回填时版本不匹配，写入被拒绝。操作只有确认协调成功才报告完成；保证的运行前提见 [ADR-0004](../adr/0004-negative-cache-for-redirects.md)。

**追问：为什么不加 Bloom Filter？**

当前先解决同一码重复查询，负缓存已覆盖这一目标。Bloom Filter 可以作为“大量不同无效短码”的扩展方案，但要处理容量、误判率、历史初始化、新建同步和恢复完整性。误判为可能存在仍需查库；系统若漏加有效短码，可能误拒绝真实映射。普通 Bloom Filter 不能安全地直接删除共享位。本项目未实现它，详细取舍见 [既有决策](../adr/0004-negative-cache-for-redirects.md#bloom-filter-与面试知识)。

## 2. 击穿：热门短码到期时如何减少查询？

`RedirectService` 用 `ConcurrentHashMap<LoadKey, CompletableFuture<LoadedRedirect>>` 保存正在进行的加载；`LoadKey` 包含短码和缓存版本。第一个请求成为加载者，其他同码同版本请求等待并复用结果。加载者取得任务后再检查一次缓存，避免上一轮刚完成却重复查库；任务成功或失败后移除。

**追问：为什么键里还要有版本？**

只按短码合并，会让创建或重新启用完成后的新请求加入旧任务，拿到旧的 404/403。缓存回填被拒绝也无法修正已经共享出去的旧结果，所以加载任务也要隔离版本。

**追问：加载者很慢或失败怎么办？**

等待者默认最多等待共享任务 200ms，超时后重读缓存，仍没有结果则独立回源；不取消其他请求使用的任务。数据库失败不会写成 404 负缓存，任务清理后允许后续重新加载。每个请求在使用共享结果时重查业务过期时间。200ms 是共享等待预算，不是整个 HTTP 请求的耗时上限。

**追问：多个应用实例能否总共只查一次？**

不能；正常的一轮交叠请求可以每实例各查一次，版本无法确认或超时还可能增加查询。当前是单应用本地展示，不引入跨实例互斥回源锁。Redis 版本校验使用 Lua，并不等于使用 Redis 分布式锁。

## 3. 雪崩：TTL 抖动和回源准入分别做什么？

对写入的业务结果，`RedisRedirectCache.jitteredTtlMillis` 将 TTL 随机缩短配置上限的 0%～10%。例如 5 分钟的上限，抖动后约为 270～300 秒；限时正缓存还要与剩余业务有效时长取较小值。版本占位不属于这里的业务结果。

**追问：为什么用随机缩短？**

它能分散部分条目的到期时间，又不超过配置 TTL 上限。缓存 TTL 用于清理和限制缓存存留，每次跳转仍检查业务有效期，不能用 TTL 替代到期判断。

**追问：Redis 整体不可用，随机 TTL 还有作用吗？**

没有。此时跳转限流按既定规则放行，缓存读取失败则独立查库，不能加入无法确认版本的共享任务。`RedirectService` 用 Semaphore 限制实际查询，每实例默认最多 4 个同时进行的跳转 SQL；没有许可立即返回 `503 REDIRECT_LOAD_BUSY`，不增加等待队列。缓存命中和仅等待共享结果的请求不占查询许可。

该限制是并发数，不是 QPS，也不是集群总容量或数据库独占连接预留。项目没有 Sentinel/Cluster、自动熔断或 Redis 故障下的成功率保证；创建和管理在 Redis 限流不可用时可能返回业务前 503。

## 4. 一致性：为什么不只在修改后删 key？

一个具体竞态：请求 A 读到旧状态后暂停；请求 B 修改数据库并删除缓存；A 恢复并将旧状态写回。单纯删 key 仍会产生旧回填。

当前做法是数据库确认提交后轮换版本，回填用 Redis Lua 原子检查当前版本是否仍匹配。旧版本或已经丢失的条目不能接受迟到回填。版本解决回填一致性，请求合并解决并发重复查询，两者不能互相替代。

MySQL 与 Redis 不构成原子事务。数据库已提交而缓存协调未确认时，返回携带短码的专门 503，仅恢复协调，不能当作回滚或盲目重发创建。即时可见依赖同一 Redis 主实例、已确认写入未丢失等运行前提；旧快照恢复的处理留在 [故障说明](../故障排查/redis-recovery.md)。

## 6. 常见比较追问

### Q1. 为什么采用 Cache Aside，而不是直接使用注解缓存？

读取顺序是先查 Redis，miss 后查 MySQL，再按版本条件回填。项目需要明确区分不存在、禁用、过期和版本占位，并控制迟到回填、逐请求有效期及失败结果，当前通过窄缓存契约显式编排。

没有使用 `@Cacheable` 来自动覆盖这些协议。注解缓存可以简化普通缓存需求，但不能仅加一个注解就声称解决了当前全部状态与并发边界。

### Q2. 负缓存与缓存 miss 有何区别？

负缓存是成功查到一个业务拒绝结果，例如 `NOT_FOUND`；miss 是缓存没有可用业务结果，仍需要查库。版本占位只用于协调，也不是 404。

数据库错误不能记作不存在；否则一次临时错误会被缓存成错误业务结论。`DISABLED` 和 `EXPIRED` 也必须保持独立状态及各自 TTL。

### Q3. 为什么没选逻辑过期、后台刷新？

这类方案可以用旧值维持响应，再由后台更新，但短链接有真实过期与禁用约束，不能简单把旧的可跳转状态继续返回。即使 Redis 值还在，每个请求也必须检查业务有效期。

当前选择有限 TTL、实例内加载合并和逐请求判断。逻辑过期不是不能使用，而是要重新定义哪些旧结果可接受、刷新失败怎么处理和状态变化怎么协调；本项目没有实现。

### Q4. 延迟双删能替代版本校验吗？

假设 A 读旧值后暂停，B 改库并第一次删缓存，延迟第二次删除后 A 才恢复回填，旧值仍能出现。固定延迟无法证明所有旧读取都已结束。

版本协议让回填明确携带读时版本，Lua 校验当前版本后再写；失配或条目丢失则拒绝写入。它也有同主实例和已确认写入不丢失等运行前提，不能包装成无条件强一致。

### Q5. 缓存击穿和正常命中的热点 key 是否一样？

击穿主要关心 miss 后的重复数据库加载；正常命中的热点则仍对同一个 Redis key 产生高频读取。实例内共享加载只用于正在进行的 miss，不能消除正常命中的 Redis 请求。

多级缓存或 key 拆分属于扩展：先看访问量、Redis 延迟与回源量，再评估额外状态同步和失效复杂度。当前没有长期本地缓存或热点 key 拆分。

### Q6. 短 TTL 能保证不被大量无效短码撑满吗？

不能。不断更换合法无效短码仍会查询并建立有限 TTL 条目，版本占位也占用空间。TTL 限制存留时间，不等于严格全局内存上限；抖动也不阻止扫描。

当前配合跳转限流和 SQL 准入缓解压力，仍需观察 key 数量、内存与拒绝比例。Bloom Filter 是否值得增加，要根据不同无效短码的真实回源压力评估，而不是为了凑技术栈。
