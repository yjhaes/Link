# 简历素材与面试边界

返回 [面试导航](README.md)。候选表述基于已实现能力与[正式验收](../测试与验证/verification.md)，按本人实际参与和能解释的内容选择，不虚构用户量、上线规模或性能收益。

## 精简候选表述

同一项目通常选两三条即可，不需要把所有实现细节都放进简历。

- 基于 Spring Boot、MyBatis-Plus 与 MySQL 实现短链接创建、过期、启禁用及跳转，采用自增发号、有界双射与 Base62 编码生成 4～8 位短码，数据库主键兜底唯一性。
- 针对缓存穿透、热点击穿和集中到期，实现分类负缓存、按短码与版本共享加载、TTL 抖动及回源并发准入；通过版本条件回填拒绝迟到旧结果。
- 使用 RabbitMQ 将访问统计网络和 SQL 移出 HTTP 线程，以 eventId 唯一键处理重投，并实现匿名 PV/UV、日趋势及访问明细查询；明确异步可见与允许漏记的边界。
- 基于 Redis Lua 令牌桶按请求组限流，区分 429、依赖不可用与回源繁忙，结合用例、HTTP 和真实设施验收核对并发及无副作用拒绝。

## 展开素材与证据限制

下列四条用于准备追问，可按岗位压缩；不把设计接受、某次低并发观察或 HTTP 拒绝速度当生产能力。

- 基于MySQL自增发号、确定性双射置换与Base62编码生成4～8位短码，以数据库主键兜底唯一性；验证编码长度、多实例创建与冲突重试。发号和映射分开提交，允许ID空洞；外观混淆不是安全防枚举。
- 针对短链接缓存穿透、击穿及集中到期，实现404/403/410分类负缓存、实例内按短码+版本合并加载与TTL随机抖动；提交后轮换版本拒绝迟到旧回填，逐请求重查到期。独立应用上下文与真实Redis验证并发协议；跨实例仍允许各自回源，Redis整体故障依靠每实例回源准入缓解压力，即时可见依赖同主实例及确认写入未丢失，旧快照恢复须受控清理。原理与追问见[缓存优化面试提纲](cache-interview.md)。
- 将访问统计网络/SQL移出HTTP线程，通过有界本地交接、confirm/return、AUTO ACK、eventId唯一键和有限重试/DLQ隔离统计工作。核验真实创建→302→异步PV/UV、重投去重、积压与重启；本地接受、broker确认、MySQL保存是三个不同成功边界，best-effort允许漏记，不保证端到端恰好一次。
- 使用真实Redis Lua令牌桶按创建/跳转/管理写/查询分组限流，验证最后令牌竞争、跨实例共享、TTL/NOSCRIPT与扣减超时不盲重试；对实际跳转SQL设置每实例4并发立即准入。Redis失败时创建/管理业务前拒绝，跳转放行仍受回源保护，429/503不产生统计副作用；不是集群总容量或分布式抗DDoS。

有限观察仅提供带条件p50/p95、成功/429/503、SQL与资源结果，不写无依据高QPS或无条件55%提升。

面试展示可按README最短步骤运行，再使用[有限观察与故障入口](../测试与验证/performance-and-failures.md)展示默认额度、故障等待和受控恢复。简历不写账号体系、网关/微服务、outbox/事务消息、可靠统计记账、Bloom Filter、自动死信补偿或完整监控平台；这些是停止线之外的内容。

## “最难的问题”回答组织

按场景、问题、改动、验证四步组织。以本人确实参与的缓存问题为例：

> 场景是创建或重新启用与旧查询重叠。只在修改后删缓存，旧查询仍可能迟到回填；只保护缓存写入，新请求还可能加入旧共享任务。我把回填和共享加载都按版本隔离，用同步点控制先后顺序、检查查询次数和返回状态，再通过真实 Redis 验证原子条件回填。保证仍依赖同一 Redis 主实例，不能覆盖旧快照回滚。

如果只是读过代码或测试，就如实说“理解并验证了这一机制”，不包装成自己处理过生产事故。其他可选场景见 [测试证据与模拟面试](测试证据与模拟面试.md)。

## 面试前核对

- 各项措施能指出源码，能说出一个具体失败场景和限制。
- “验证通过”对应真实记录的源码版本和测试环境。
- 性能数据有同条件基线；没有则只陈述机制与正确性结果。
- 没有把单节点/实例内能力写成生产高可用或集群总容量。
- 没有把 Bloom Filter、outbox、分布式锁等扩展知识写成已实现。
